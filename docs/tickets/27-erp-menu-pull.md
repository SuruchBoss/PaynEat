## ปัญหา
ticket 25 ทำให้วัตถุดิบและสาขามาจาก ERP แล้ว แต่เมนู ราคา และสูตรยังแก้ในเครื่องได้ ERP ต้องแปลงยอดขายเป็นการใช้วัตถุดิบ
ด้วยสูตรของตัวเอง (ERP #17) ถ้าเมนูใน POS กับใน ERP ไม่ตรงกัน ยอดขายจะแปลงไม่ได้และถูกกองไว้เป็น "failed" ใน ERP

## ทำไมสำคัญ
เชนต้องเปลี่ยนราคาหรือเพิ่มเมนูที่เดียวแล้วทุกสาขาได้พร้อมกัน และทุกบรรทัดที่ขายต้องมีรหัสที่ ERP รู้จัก ไม่งั้นเส้นทาง
"จากจานย้อนกลับไปถึง lot" ขาดตรงกลาง

## ขอบเขตงาน
- **ดึงตามเวอร์ชันแบบเดิมของ ticket 25** แต่รองรับชนิดข้อมูลใหม่ในสัญญา v1.1: `menu_item`, `menu_price`, `modifier_group`
  (พร้อมตัวเลือกทั้งหมด), `menu_recipe`, `modifier_recipe`
  - ชนิดที่ POS ไม่รู้จักให้ข้ามไปโดยไม่ error (ตามกฎของสัญญา) — `menu_recipe` และ `modifier_recipe` สัญญาอนุญาตให้ข้ามได้
  - ไม่มีอะไรถูกลบจาก ERP: `active: false` แปลว่าเลิกขาย/เลิกเสนอตัวเลือกนั้น ตัวเลือกไม่หายไปจากรายการ
- **จับคู่ด้วยรหัสของ ERP**: เพิ่มคอลัมน์รหัส ERP ให้ `menu_items` และ `options` (null ในโหมดเดี่ยว) ใช้รหัสนี้ใน sales event
  ของ ticket 26
- **เมนู**: ชื่อไทย/อังกฤษ หมวด ขายตามน้ำหนัก (`soldBy: weight` → `sold_by_weight`) มาจาก ERP ส่วนที่เป็นของหน้าร้านล้วนๆ
  ยังแก้ในเครื่องได้: รูป, ลำดับ, แนะนำ, เวลาเตรียม, ปิดขายชั่วคราว (`is_available`), บาร์โค้ดและ PLU ตาชั่ง
  - **หมวดเป็นป้าย ไม่มีรหัสหมวด**: จัดเมนูไว้ใต้หัวข้อตาม `categoryTh`/`categoryEn` เมนูที่ป้ายเดียวกันอยู่หัวข้อเดียวกัน
    ERP เปลี่ยนชื่อหมวดโดยส่งป้ายใหม่มากับแต่ละเมนู เมนูจึงย้ายไปหัวข้อใหม่เอง หมวดที่ไม่เหลือเมนูให้ซ่อน
- **ราคา**: แปลงสตริงบาท (ทศนิยมไม่เกินสตางค์) เป็นสตางค์ตามกติกาเงินเดิมของ repo
  - เก็บแถว `menu_price` ทุกแถวตาม `id` ถ้า `id` เดิมมาอีกให้เขียนทับ (ERP แก้ราคาได้เฉพาะก่อนวันมีผล)
  - ราคามีผลตั้งแต่ `effectiveFrom` (วันทำการตามเขตเวลาของเชน) จนกว่าแถวถัดไปของขอบเขตเดียวกันจะเริ่ม ราคาที่มีผลในอนาคต
    เก็บไว้ก่อน แล้วใช้เมื่อถึงวัน (ตรวจทุกรอบดึงและทุกนาที) ห้ามเปลี่ยนราคาของบิลที่เปิดอยู่
  - แถว `locationCode: null` คือราคากลางของเชน มีราคาเสมอ แถวที่มีรหัสสาขาคือราคาของสาขานั้น
  - **แถวของสาขาที่ `price: null` = สาขานั้นกลับไปใช้ราคากลาง** ตั้งแต่ `effectiveFrom` ของแถวนั้น รวมถึงราคากลางที่เปลี่ยน
    ภายหลัง จนกว่าสาขาจะได้ราคาของตัวเองอีกครั้ง **ห้ามแปลง `null` เป็น 0 เด็ดขาด** (ราคา 0 = ขายฟรีแบบเงียบ ผิดเกณฑ์
    "เงินไม่ผิดแบบเงียบ" ของ DECISIONS #93) และห้ามปฏิเสธแถวนี้
  - ราคาของสาขาในวันหนึ่ง: ถ้าแถวล่าสุดของสาขาที่เริ่มแล้วมีราคา ใช้ราคานั้น ไม่งั้น (ยังไม่มีแถวของสาขา หรือแถวล่าสุดเป็น
    `price: null`) ใช้ราคากลางที่มีผลวันนั้น
  - เมนูที่ไม่มีราคามีผลเลย **ขายไม่ได้** แสดงเหตุผลที่หน้าขาย ห้ามใช้ 0 แทน
  - POS ยังไม่มีราคาแยกสาขาภายใน instance เดียว ถ้า POS instance เดียวดูแลหลายสาขาแล้วราคาที่มีผล (คิดตามกติกาข้างบน
    รวมการกลับไปใช้ราคากลาง) ต่างกัน ให้คงราคาเดิม แสดงความขัดแย้งที่หน้าการเชื่อมต่อ และแนะนำให้แยก POS instance ตาม
    โซนราคา — ห้ามเลือกราคาใดราคาหนึ่งเงียบๆ
  - ราคาที่ได้คือราคาขายตามที่แสดง ภาษียังคิดใน POS เหมือนเดิม
- **ตัวเลือก**: กลุ่มตัวเลือกของ ERP ผูกกับหลายเมนูได้ (`modifierGroupCodes` ของเมนู ตามลำดับที่แสดง) แต่ POS ผูกกลุ่มกับ
  เมนูทีละเมนู ให้สร้างสำเนาต่อเมนูโดยทุกสำเนาถือรหัส ERP เดียวกัน และเมื่อกลุ่มเปลี่ยนต้องอัปเดตทุกสำเนา
  - `minSelections`/`maxSelections` → `min_select`/`max_select`
  - `priceChange` เป็น 0 หรือ **ติดลบได้** บวกต่อหน่วยที่ขาย (ต่อชิ้น หรือต่อกิโลกรัมสำหรับเมนูชั่งน้ำหนัก ซึ่ง
    `lineTotalFor` คิดแบบนี้อยู่แล้ว) ค่าที่มาจาก ERP เขียนลง `options.price_delta` ได้ตรงๆ (คอลัมน์ไม่มีข้อจำกัดเรื่อง
    ค่าติดลบ) ส่วน `priceDelta: min(0)` ใน `menu.schema.js` เป็นของหน้าแก้ไขในเครื่อง ซึ่ง ticket นี้ทำให้อ่านอย่างเดียวในโหมดเชื่อมต่อ
  - ถ้าราคาเมนูรวมตัวเลือกที่เลือกได้ต่ำกว่า 0 ต่อหน่วย ให้ปฏิเสธการสั่งบรรทัดนั้นพร้อมเหตุผล ห้ามตัดเป็น 0 เงียบๆ
    (สัญญาไม่ได้ห้ามกรณีนี้ไว้ ถ้าเจอจริงให้แจ้ง ERP PO)
- **สูตรเมนู**: mirror เวอร์ชันที่มีผลปัจจุบันลง `menu_item_ingredients` เพื่อแสดงผลเท่านั้น (สูตรของตัวเลือกไม่ต้อง mirror
  เพราะ ERP เป็นคนแปลงยอดขาย) และตาม ticket 25 ยอดวัตถุดิบในเครื่องไม่ใช่ความจริงในโหมดเชื่อมต่อ
- **ตอนเชื่อมต่อครั้งแรก (switch-over)**: หน้าจอแสดงเมนูในเครื่องที่ยังไม่มีรหัส ERP ให้ admin เลือกทีละรายการว่า
  **ผูกกับเมนูของ ERP** หรือ **ซ่อน** (ประวัติการขายเดิมไม่หาย)
  - เมนูที่ยังไม่ผูกขายไม่ได้ในโหมดเชื่อมต่อ ไม่งั้น ERP จะแปลงยอดขายไม่ได้
- **หน้าจัดการเมนู/ราคา/ตัวเลือก/สูตรเป็นอ่านอย่างเดียว** ในส่วนที่ ERP เป็นเจ้าของ มีป้าย "จัดการใน PaynEat ERP" และ API
  ปฏิเสธด้วย 409 พร้อมเหตุผล
- **telemetry**: log การดึงรอบที่มีข้อมูลเมนู บอกจำนวนแต่ละชนิดและเวอร์ชัน ความขัดแย้งด้านราคาเป็น `WARNING`
- **contract test**: ตรวจ response ตัวอย่างกับไฟล์สัญญา v1.1 ใน CI (ปักเวอร์ชันไว้)

## ขอบเขตที่ตั้งใจไม่ทำ
- ราคาแยกสาขาภายใน POS instance เดียว
- ส่งเมนูที่สร้างใน POS กลับขึ้นไปที่ ERP (ทิศทางเดียว: ERP → POS)
- feed ยอดคงเหลือจาก ERP เพื่อขึ้นป้าย "หมด" อัตโนมัติ (หลัง ERP v1)

## เทสต์
backend: stub server ของ ERP ในเทสต์ ครอบคลุมการดึงแต่ละชนิด ราคาในอนาคต ราคาแยกสาขาที่ขัดกัน switch-over และการปฏิเสธ
การแก้ในโหมดเชื่อมต่อ และเคสราคาตามสัญญา 1.1 อย่างน้อย: สาขามีราคาเอง → `price: null` → ราคากลางเปลี่ยนภายหลัง (สาขาตาม)
→ สาขาได้ราคาเองอีกครั้ง, แถว `id` เดิมถูกแก้ก่อนวันมีผล, เมนูที่ไม่มีราคามีผล, ตัวเลือกติดลบบนเมนูนับชิ้นและชั่งน้ำหนัก
แอป: controller test ของหน้า switch-over และหน้าจัดการเมนูในโหมดอ่านอย่างเดียว
