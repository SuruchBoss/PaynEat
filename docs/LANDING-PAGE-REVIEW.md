## 1. บั๊กอัตราส่วนภาพ — ภาพถูกบีบแนวนอนทั้งหน้า

### อาการ

ภาพหน้าจอทุกใบถูกบีบให้แคบกว่าของจริง ใบที่หนักที่สุดคือแดชบอร์ดเว็บ
ซึ่งเหลือความกว้างแค่ **45%** ของสัดส่วนที่ถูกต้อง

| ภาพ | ขนาดจริง | ratio จริง | ratio ที่ render | ผิดไปเท่าไร |
|---|---|---|---|---|
| แดชบอร์ดเว็บ | 1180×737 | 1.6011 | 0.7271 | บีบเหลือ 45% |
| จอครัวแท็บเล็ต | 1180×824 | 1.4320 | 0.7774 | บีบเหลือ 54% |
| ผังโต๊ะ (hero) | 460×995 | 0.4623 | 0.3156 | บีบเหลือ 68% |
| หน้าเก็บเงิน | 420×908 | 0.4626 | 0.3458 | บีบเหลือ 75% |
| ผังโต๊ะ โหมดปกติ | 460×995 | 0.4623 | 0.3015 | บีบเหลือ 65% |
| ผังโต๊ะ คอนทราสต์สูง | 420×908 | 0.4626 | 0.3304 | บีบเหลือ 71% |

### สาเหตุที่แท้จริง

แท็ก `<img>` ทุกใบมี attribute `width` และ `height` กำกับไว้ (ซึ่งถูกต้อง — ช่วยกัน layout shift)
แต่ CSS เขียนไว้แค่:

```css
.phone img{display:block;width:100%;border-radius:23px}
.slab img{display:block;width:100%}
```

`width:100%` ทับค่าความกว้างจาก attribute แต่ **ไม่มีอะไรทับความสูง** ความสูงจึงค้างอยู่ที่
ค่าจาก attribute (เช่น `height="737"`) ขณะที่ความกว้างถูกบีบลงมาตามคอลัมน์ — ภาพเลยยืดในแนวตั้ง

จุดที่ทำให้หลุดสายตา: skeleton ของ Artifact ใส่ `img{max-width:100%}` มาให้อยู่แล้ว
เลยรู้สึกเหมือนเรื่องภาพถูกจัดการแล้ว แต่ `max-width` ไม่ได้แตะ `height` เลย

### ทางแก้

```css
img{height:auto}                                              /* ครอบทุกใบ */
.phone img{display:block;width:100%;height:auto;border-radius:23px}
.slab img{display:block;width:100%;height:auto}
```

ต้องมีกฎ `img{height:auto}` ตัวกลางด้วย เพราะภาพคู่เทียบคอนทราสต์ใช้ `class="phone"`
บน `<img>` โดยตรง ไม่ได้อยู่ใน wrapper — selector `.phone img` (descendant) จึงไม่ match

### ผลหลังแก้

| ภาพ | ratio จริง | ratio ที่ render | |
|---|---|---|---|
| แดชบอร์ดเว็บ | 1.6011 | 1.6011 | ✅ |
| จอครัวแท็บเล็ต | 1.4320 | 1.4321 | ✅ |
| ผังโต๊ะ (hero) | 0.4623 | 0.4623 | ✅ |
| หน้าเก็บเงิน | 0.4626 | 0.4626 | ✅ |

### กรณีที่ดู "ผิด" แต่ถูก

ภาพคู่เทียบคอนทราสต์ 2 ใบ วัด bounding box ได้ `300×630` ทั้งที่ ratio จริงคือ 0.4623
(ควรได้ 300×649) — **ไม่ใช่การบิดเบี้ยว** เพราะ `.phone` อยู่บนตัว `<img>` เอง
กรอบมือถือ (padding 7px + border 1px ต่อด้าน) จึงถูกนับรวมในกล่อง:

```
ความกว้างเนื้อภาพ = 300 − (7×2) − (1×2) = 284
ความสูงเนื้อภาพ   = 284 ÷ 0.4623        = 614.3
ความสูงกล่องรวม   = 614.3 + 16          = 630.3  ✅ ตรงกับที่วัดได้
```

### ภาพคู่เทียบไม่ได้อยู่บนสเกลเดียวกัน

แยกจากบั๊กข้างบน: ภาพ A/B ในหัวข้อคอนทราสต์ย่อมาคนละขนาด — ใบซ้าย `460×995`
ใบขวา `420×908` ทั้งที่ golden ต้นทางเป็น `780×1688` เหมือนกัน

ในภาพเปรียบเทียบ สิ่งที่ต่างกันควรมีแค่สิ่งที่ตั้งใจให้ต่าง ถ้าใบขวาเบลอกว่าเพราะย่อมาเล็กกว่า
คนดูจะแยกไม่ออกว่าความต่างที่เห็นมาจากโหมดคอนทราสต์ หรือมาจากคุณภาพไฟล์
จึงเข้ารหัสใบขวาใหม่ที่ `460×995` ให้เท่ากันทั้งคู่ (18.5 KB)

## 2. ตัวเลขคอนทราสต์จับคู่ผิดเคส

### สิ่งที่หน้าเว็บเขียนไว้ (ผิด)

> ป้ายสถานะ "รอทำ" เคยเป็นตัวหนังสือขาวบนเหลืองอำพัน ซึ่งดูเผิน ๆ ก็อ่านได้
> แต่วัดจริงแล้วอยู่ที่ **1.94:1** — ต่ำกว่าเกณฑ์ WCAG กว่าครึ่ง
> **โหมดคอนทราสต์สูง**ดันทุกตัวถึงระดับ AAA

ผิด 2 ชั้นซ้อนกัน: เอาตัวเลขจาก 2 เคสที่ไม่เกี่ยวกันมาต่อเป็น before/after เดียว
แล้วยังยกเครดิตปลายทางให้ผิดฟีเจอร์

### ตัวเลขจริง

คำนวณย้อนจาก palette จริงใน `app/lib/app/theme/app_colors.dart` ด้วยสูตร WCAG relative luminance:

| คู่สี | อัตราส่วน | คือเคสอะไร |
|---|---|---|
| `#FFFFFF` บน `warning #F59F00` | **2.13:1** | ป้ายขาวแบบเดิม ← before ที่ถูกต้อง |
| `textPrimary #1A1D21` บน `warning #F59F00` | **7.93:1** | ป้ายเข้มแบบใหม่ ← after ที่ถูกต้อง |
| `warningInk #7A3806` บน `warning #F59F00` | 4.11:1 | โหมดคอนทราสต์สูง |
| ตัวหนังสือสีสดบนพื้น tint ของตัวเอง | **1.94:1** | หัวคอลัมน์จอครัว — **คนละเคส** |

ข้อสรุป 2 ข้อ:

1. **1.94 ไม่ใช่เคสป้ายขาวบนเหลือง** — เป็นหัวคอลัมน์จอครัวที่วางตัวหนังสือสีสด
   บนพื้น tint ของสีตัวเอง ซึ่งเป็นคนละปัญหากันคนละที่
2. **7.93 ไม่ได้มาจากโหมดคอนทราสต์สูง** — มาจากโหมดปกติที่เปลี่ยนมาใช้
   "พื้นสีสด + ตัวหนังสือเข้ม" ผ่าน `AppColors.onColor()` โหมดคอนทราสต์สูงให้ 4.11
   ซึ่งน้อยกว่าด้วยซ้ำ (เพราะเลือกใช้เฉด ink ไม่ใช่ `textPrimary`)

### แก้เป็น

สถิติ hero เปลี่ยนเป็น **2.13 → 7.93** ซึ่งเป็น before/after ของคู่เดียวกันจริง
และยังเป็นตัวเลขที่แรงกว่าเดิม พร้อมเขียนย่อหน้าใหม่ให้ตรงกับการตัดสินใจจริง
(คงพื้นสีสดไว้ แล้วเลือกสีตัวหนังสือจากสีพื้น) และกำกับเกณฑ์ **AA = 4.5:1**
ไว้ในคำอธิบายใต้ตัวเลข เพื่อให้คนอ่านตรวจสอบเองได้ว่า 2.13 นั้นต่ำแค่ไหน

### บทเรียน

ตัวเลขคอนทราสต์ที่เคยคำนวณไว้ในเอกสารตรวจ UX มีหลายคู่ที่หน้าตาใกล้กัน
การหยิบมาใช้ต่อโดยไม่ย้อนไปคำนวณใหม่จากโค้ด ทำให้สลับคู่กันได้ง่ายมากโดยไม่รู้ตัว
**ตัวเลขทุกตัวที่จะเอาไปอ้างในหน้าที่คนนอกอ่าน ต้องคำนวณใหม่จาก source of truth เสมอ
ไม่ใช่คัดลอกจากสรุปรอบก่อน**

## 6. วิธีตรวจซ้ำ

### นับเทสต์

```bash
cd backend && npm test     # อ่านบรรทัด "# pass"
cd app && CI=true flutter test   # อ่านตัวเลขท้าย "+N: All tests passed!"
```

> ต้องมี `CI=true` ไม่งั้น Flutter จะพ่น warning เรื่องรันด้วย root ออก stderr

### คำนวณอัตราส่วนคอนทราสต์

```python
def lum(h):
    h = h.lstrip('#')
    c = [int(h[i:i+2], 16) / 255 for i in (0, 2, 4)]
    c = [x/12.92 if x <= 0.03928 else ((x+0.055)/1.055)**2.4 for x in c]
    return 0.2126*c[0] + 0.7152*c[1] + 0.0722*c[2]

def cr(a, b):
    l1, l2 = sorted([lum(a), lum(b)], reverse=True)
    return (l1 + 0.05) / (l2 + 0.05)
```

### วัดอัตราส่วนภาพที่ render จริง

เทียบ `naturalWidth/naturalHeight` กับ `getBoundingClientRect()` ของทุก `<img>`
ถ้าสองค่าไม่ตรงกันแปลว่าภาพถูกบีบ — ยกเว้นกรณีที่ตัว `<img>` มี padding/border เอง
ซึ่งต้องหักออกก่อนเทียบ (ดูหัวข้อ 1)
