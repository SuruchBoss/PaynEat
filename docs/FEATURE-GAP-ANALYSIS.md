# PaynEat POS — Feature Gap Analysis (มุมมอง PO)

วันที่วิเคราะห์: 2026-09-09
ผู้วิเคราะห์: PO review (ผ่าน Claude Code) โดยอ่านโค้ดจริง + README + `docs/DECISIONS.md`

เอกสารนี้สรุปว่าฟีเจอร์ POS พื้นฐานอะไร **มีอยู่แล้ว** และอะไร **ยังขาด** เทียบกับสิ่งที่ POS
ร้านอาหารทั่วไปต้องมีเพื่อใช้งานจริง (ไม่ใช่แค่ demo/portfolio) ใช้เป็น input สำหรับตัด ticket
พัฒนาต่อ — ดู tickets ที่เกี่ยวข้องใน `docs/tickets/` (สร้างจากเอกสารนี้)

## สิ่งที่มีอยู่แล้ว (ยืนยันจากโค้ดจริง)

- ผังโต๊ะ + สถานะ (available/occupied/reserved/billing), ย้ายโต๊ะ, รวมบิล (merge)
- สั่งอาหาร + modifier/option group, บันทึกครัว, ตะกร้ารวมรายการซ้ำอัตโนมัติ
- ครัว (KDS) realtime ผ่าน Socket.IO, แจ้งเตือนออเดอร์ค้างนาน
- ชำระเงิน 4 ช่องทาง (cash/qr/card/transfer — `qr` แสดง QR พร้อมเพย์จริงให้ลูกค้าสแกน ดู
  `docs/tickets/16-promptpay-qr.md`), แบ่งจ่ายหลายช่องทาง, แบ่งบิลตามรายการ/ต่อคน
- ส่วนลดแบบ manual ต่อบิล (%, บาท) และโปรโมชันแบบตั้งเงื่อนไขล่วงหน้า (percent/amount/bogo,
  เงื่อนไขวัน/เวลา/เมนู-หมวดหมู่/ยอดขั้นต่ำ, auto-apply หรือรับโค้ดส่วนลด)
- ใบเสร็จบนหน้าจอ + พิมพ์จริงผ่านเครื่องพิมพ์ความร้อน ESC/POS บนวง LAN/WiFi
- เปิด/ปิดกะ + กระทบยอดเงินสด, คืนเงินหลังชำระเงินแล้ว (เต็มจำนวน/บางส่วน)
- Offline mode สำหรับสั่งอาหารเพิ่มเข้าออเดอร์เดิม (queue ในเครื่อง + sync อัตโนมัติ)
- Dashboard + รายงานย้อนหลัง (ยอดขายรายวัน, สินค้าขายดี, สัดส่วนการชำระเงิน)
- จัดการเมนู/หมวดหมู่, จัดการพนักงาน + RBAC 5 role (admin/manager/waiter/cashier/kitchen)
- ตั้งค่าร้าน (VAT rate, service charge, VAT-inclusive toggle)
- คำนวณ VAT + service charge ตรงกันทั้ง frontend/backend มี test คุม

ที่มา: `README.md`, `docs/DECISIONS.md`, `backend/src/db/schema.sql`,
`app/lib/features/**`, `backend/src/modules/**`

## Gap ที่พบ (เรียงตามความสำคัญ)

### 🔴 Critical — บล็อกการใช้งานจริง (ร้านจริงต้องมี ไม่ใช่ของเสริม)

✅ **ทั้ง 5 รายการทำครบแล้ว** (ดูรายละเอียดที่ `docs/tickets/01-04-*.md` และ
`docs/DECISIONS.md` #11/#13 สำหรับขอบเขตที่ตั้งใจจำกัดไว้) — ระหว่างตรวจโค้ดจริงซ้ำอีกรอบ
(2026-09-15) เคยพบ gap ใหม่ที่ไม่เคยอยู่ในรายการนี้มาก่อนคือ **#16 PromptPay QR ยังเป็นของปลอม**
ซึ่งกระทบความน่าเชื่อถือมากกว่ารายการอื่นที่เหลือทั้งหมดเพราะเป็นสิ่งที่ลูกค้าเจอวันแรกที่ใช้งาน —
**ปิดแล้ว** ดู `docs/tickets/16-promptpay-qr.md`

| # | ฟีเจอร์ที่ขาด | ทำไมสำคัญ | สถานะ |
|---|---|---|---|
| 1 | เปิด/ปิดกะ + กระทบยอดเงินสด (Shift & Cash Drawer Reconciliation) | ไม่มี table `shift`/`cash_session` เลย ร้านจริงต้องนับเงินตั้งต้น/ปิดกะเทียบยอดระบบ ไม่งั้นตรวจสอบเงินหายไม่ได้ | ✅ เสร็จแล้ว |
| 2 | คืนเงินหลังชำระเงินแล้ว (Refund) | มีแค่ "cancel" ก่อนเสิร์ฟ/ก่อนจ่าย ไม่มี flow คืนเงินหลังจ่ายสำเร็จ ไม่มี table `refunds` เลย | ✅ เสร็จแล้ว |
| 3 | พิมพ์ใบเสร็จจริง (Thermal/ESC-POS printer) | ปัจจุบันมีแค่ใบเสร็จบนจอ (ตั้งใจไม่ทำตาม `docs/DECISIONS.md` เพราะเป็น demo) แต่ร้านจริงต้องมี | ✅ เสร็จแล้ว (LAN/WiFi — Bluetooth/USB ยังไม่ทำ ดู #11) |
| 4 | Offline mode | เน็ตร้านอาหารหลุดบ่อย ตอนนี้ order พึ่ง backend ตลอด ไม่มี local queue + sync กลับ | ✅ เสร็จแล้ว (เฉพาะสั่งเพิ่มเข้าออเดอร์เดิม ดู #13) |
| 16 | **PromptPay QR / payment gateway จริง** | `qr` ใน `PAYMENT_METHODS` เคยเป็นแค่ label ให้ cashier กดยืนยันเอง เหมือน `card`/`transfer` ทุกอย่าง — ไม่มี generate QR ตามมาตรฐาน PromptPay คู่แข่งในตลาดไทยทุกเจ้ามีเป็นมาตรฐานขั้นต่ำ | ✅ เสร็จแล้ว (generate QR จริงตามมาตรฐาน EMV QR — ยังไม่มี payment gateway/callback ตรวจสอบอัตโนมัติตามที่ตั้งใจแยกขอบเขตไว้ ดู `docs/tickets/16-promptpay-qr.md`) |

## คำแนะนำลำดับพัฒนา (Roadmap)

1. ✅ **Sprint แรก (เสร็จแล้ว)**: 4 รายการ 🔴 (เปิด-ปิดกะ, refund, พิมพ์ใบเสร็จจริง, offline mode) — เป็น "ของที่ POS ทุกตัวต้องมี" ไม่ใช่ของเสริม
2. ✅ **#16 PromptPay QR จริง** (เสร็จแล้ว) และ ✅ **#17 Audit ระดับบัญชี/การเงิน** (เสร็จแล้ว) —
   ทั้งคู่เจอระหว่างตรวจโค้ดซ้ำ (2026-09-15) เคยเป็น gap ที่เหลือใน 🔴 Critical/🟠 High ตอนนั้น
   ตอนนี้ audit ที่ผู้ใช้ขอไว้ตั้งแต่ต้นครบทั้งสองฝั่งแล้ว (ผู้จัดการร้าน ✅ / บัญชี ✅)
3. ✅ **เฟส 2 (เสร็จแล้วทั้ง 4 รายการ)**: โปรโมชัน + สต๊อก + ใบกำกับภาษี + audit log — เพื่อแข่งขันกับ POS เจ้าอื่นได้
4. **เฟส ขยายธุรกิจ**: 🟡 ลูกค้า/loyalty ✅ และ takeaway/delivery ✅ เสร็จแล้วทั้งคู่ — เหลือ
   multi-branch, export รายงาน
5. **Backlog**: 🟢 nice-to-have ตามความเหมาะสม

gap ข้อใดในตารางด้านบนและไม่ได้เปิด gap ใหม่** ส่วน #21 (audit log) **ปิด gap ข้อ 8**, #22
(ลูกค้า/แต้มสะสม) **ปิด gap ข้อ 9**, #23 (takeaway/delivery) **ปิด gap ข้อ 10**, #26
(PromptPay QR) **ปิด gap ข้อ 16**, และ #27 (audit บัญชี/การเงิน) **ปิด gap ข้อ 17** โดยตรง — #25
(order audit trail) เป็นคำขอเพิ่มเติมนอกเหนือจาก gap analysis เดิม ไม่ได้ปิด/เปิด gap ข้อใดในตาราง
เช่นกัน (ดู `docs/tickets/13-order-audit-trail.md`) — #28 (ปิดรู audit log ที่เหลือ: เปิด/ปิดกะ,
รับชำระเงิน, กรอก/ถอดโค้ดส่วนลด) เป็นการแก้ต่อยอดจาก #27 พบระหว่าง self code-review ไม่ใช่ gap ใหม่
ในตารางเช่นกัน — บันทึกไว้เพื่อให้เอกสารตรงกันตามกฎใน `CLAUDE.md`

- **#16 ใบเสร็จแสดงเงินที่ลูกค้ายื่นมา** — แก้ตัวเลขบนใบเสร็จที่บวกแล้วไม่ตรงกับเงินที่ยื่นให้จริง
  เกี่ยวข้องกับข้อ 12 (Export รายงาน / Z-report) ตรงที่ถ้าจะทำใบกำกับภาษีหรือรายงานปิดวันในอนาคต
  ต้องแยกให้ชัดว่ามุมมองไหนใช้ "เงินที่ยื่นมา" และมุมมองไหนใช้ "ยอดที่ตัดเข้าบิล"
- **#17 AppClock + ตรึงนาฬิกาตอนถ่ายภาพ** — ทำให้ภาพหน้าจอถ่ายซ้ำได้ผลเหมือนเดิมทุกไบต์
  ส่งผลต่อข้อ "Flutter integration test กับ backend จริง" ใน 🟢 Nice-to-have ตรงที่ตอนนี้มีฐาน
  ให้ทำ visual regression test ได้แล้ว (ภาพนิ่ง → ภาพที่ขยับใน diff แปลว่า UI เปลี่ยนจริงเสมอ)
- **#20 Security hardening batch (OWASP Top 10)** — แก้ช่องโหว่ 7 จุดที่พบจาก security review
  (broken access control, hardcoded secret, broken authentication, security misconfiguration)
  ไม่เกี่ยวกับข้อ 8 (Audit log) โดยตรงเพราะเป็นคนละเรื่อง (ป้องกันช่องโหว่ vs บันทึกว่าใครทำอะไร)
  แต่เกี่ยวเนื่องกัน — ตอนนั้นข้อ 8 ยังเป็น gap ที่เปิดอยู่ (ปิดแล้วโดย #21 ด้านล่าง)
- **#21 Audit log** — **ปิดข้อ 8** โดยตรง บันทึก action เสี่ยงครบตามที่ทิกเก็ตกำหนด พร้อมขยาย
  scope เพิ่ม `user.role_change`/`user.password_reset`/`tax_invoice.void` ซึ่งเป็นการกระทำที่
  เสี่ยงแบบเดียวกันและต่อยอดโดยตรงจากช่องโหว่ privilege escalation ที่แก้ไปแล้วใน #20
- **#22 ลูกค้า/แต้มสะสม** — **ปิดข้อ 9** โดยตรง ผูกออเดอร์กับลูกค้าแบบ optional + สะสม/ใช้แต้ม
  ตามอัตราที่ตั้งค่าได้ + หน้าประวัติการซื้อรายคนสำหรับ admin/manager ครบตาม acceptance criteria
- **#26 PromptPay QR** — **ปิดข้อ 16** โดยตรง generate QR พร้อมเพย์จริงตามมาตรฐาน EMV QR
  ให้ลูกค้าสแกนจ่ายได้ (ยังไม่มี payment gateway/callback อัตโนมัติตามขอบเขตที่ตั้งใจไว้)
- **#27 Audit ระดับบัญชี/การเงิน** — **ปิดข้อ 17** โดยตรง แก้ราคาเมนู/สร้าง-แก้-ลบโปรโมชัน/ปรับสต๊อก
  มือถูกบันทึก audit log ครบ (ต่อยอดจาก #21/#25) เพิ่ม export CSV (`GET /audit-logs/export` —
  เว็บเท่านั้น ดู `docs/DECISIONS.md` #27) และ date range picker บนหน้า "ประวัติการทำรายการ" ที่
  ค้างมาตั้งแต่ #21
- **#28 ปิดรู audit log ที่เหลือ** — ต่อยอดจาก #27 ไม่ได้ปิด gap ใหม่ในตาราง เพิ่ม audit log ให้เปิด/
  ปิดกะ (`shift.open`/`shift.close`), รับชำระเงิน (`payment.pay`), และกรอก/ถอดโค้ดส่วนลด
  (`order.promotion_redeem`/`order.promotion_remove` — จุดหลังเพิ่ม transaction ห่อด้วยเพราะเดิม
  ไม่มี) ดู `docs/DECISIONS.md` #28
- **#33 ผู้ช่วย AI ถามตอบข้อมูลร้าน** — เช่นเดียวกับ #25 เป็นฟีเจอร์เชิงจุดขาย/นวัตกรรมนอกเหนือจาก gap
  analysis เดิม (`docs/tickets/15-ai-ask-your-data.md`) **ไม่ได้ปิด/เปิด gap ข้อใดในตาราง** — เชื่อม
  Claude API เข้ากับ endpoint เดิมของระบบผ่าน tool-calling เท่านั้น (ไม่แต่งตัวเลขเอง) ดู
  `docs/DECISIONS.md` #33
- **#23 Takeaway/Delivery** — **ปิดข้อ 10** โดยตรง เปิดออเดอร์กลับบ้าน/เดลิเวอรีได้โดยไม่ต้องผูกโต๊ะ
  พร้อมเลขคิวรับอาหาร (เฉพาะ takeaway) + KDS แยกป้าย/ไอคอนทั้ง 3 ประเภทชัดเจน — ยังไม่เชื่อม
  แพลตฟอร์มเดลิเวอรีจริง (Grab/LINE MAN) ตามที่ตั้งใจแยกเป็นทิกเก็ตย่อยต่างหาก

**`backend/src/modules/payments/payment.schema.js`** กำหนด
`PAYMENT_METHODS = ['cash', 'qr', 'card', 'transfer']` เป็น enum เฉยๆ — `qr` ถูกจัดการเหมือน
`card`/`transfer` ทุกประการ (มีแค่ช่อง `reference` ให้กรอกข้อความอิสระ) **ไม่มีการ generate QR

ว่าลูกค้าจ่ายเงินจริง** — ค้นทั้ง `app/` และ `backend/` ไม่พบ package หรือโค้ดที่เกี่ยวกับ
PromptPay/QR generation เลยแม้แต่ไฟล์เดียว

**ทำไมจัดเป็น 🔴 Critical ไม่ใช่ 🟡 nice-to-have:** POS คู่แข่งในตลาดไทยทุกเจ้า (FoodStory,
Loyverse ฯลฯ) มี PromptPay QR จริงเป็นมาตรฐานขั้นต่ำ ถ้าร้านเอาไปใช้จริงโดยเข้าใจว่า "QR" คือรับ
เงินผ่านระบบจริง ทั้งที่จริงเป็นแค่ปุ่มให้กดยืนยันเองว่า "ลูกค้าโอนแล้ว" (cashier ต้องไปเช็คสลิป/
แอปธนาคารเองนอกระบบ) มีความเสี่ยงทั้งเรื่อง trust และเงินขาด/หายที่ตรวจสอบย้อนหลังไม่ได้ — เป็น
gap เดียวที่เหลืออยู่ใน 🔴 Critical หลังจากรายการ 1-4 เดิมทำครบแล้ว

**ขอบเขตแนะนำสำหรับ ticket ถัดไป:** อย่างน้อยควร generate QR code ตาม PromptPay standard

อัตโนมัติ) ก็ตาม — เป็นก้าวแรกที่ทำได้เร็วและกระทบภาพลักษณ์มากที่สุด
