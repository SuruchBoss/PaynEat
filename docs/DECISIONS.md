# บันทึกการตัดสินใจเชิงออกแบบ

เอกสารนี้เก็บ **เหตุผล** เบื้องหลังทางเลือกสำคัญในโปรเจกต์ พร้อมข้อเสียที่ยอมรับ
เขียนไว้เพื่อให้คนที่มาอ่านโค้ด (รวมถึงตัวเองในอีก 6 เดือน) เข้าใจว่าทำไมถึงเลือกทางนี้

---

## 1. เก็บจำนวนเงินเป็นสตางค์ (integer) ไม่ใช่ทศนิยม

**ปัญหา** — `0.1 + 0.2 !== 0.3` ในทุกภาษาที่ใช้ IEEE 754 พอเอามาคิดบิลหลาย ๆ ครั้ง ยอดจะเพี้ยนทีละสตางค์
ซึ่งในระบบที่เกี่ยวกับเงินถือว่ารับไม่ได้

**ที่เลือก** — ฝั่ง backend เก็บทุกจำนวนเงินเป็นจำนวนเต็มหน่วยสตางค์ (`120.50 บาท → 12050`)
แล้วแปลงกลับเป็นบาทเฉพาะตอนส่งออกทาง API

**ข้อเสียที่ยอมรับ** — ต้องมี `toSatang()` / `toBaht()` คั่นทุกจุดที่รับ-ส่งข้อมูล ถ้าลืมจะเพี้ยน 100 เท่าทันที
จึงรวมไว้ที่ `core/money.js` ที่เดียว และบังคับให้ mapper เป็นทางผ่านเดียวที่แปลงค่า

**ทางเลือกที่ไม่ได้เลือก** — ใช้ decimal library เพราะเพิ่ม dependency และช้ากว่าโดยไม่จำเป็นสำหรับสเกลนี้

---

## 2. ตรรกะคิดบิลเขียน 2 ที่ (Dart + JavaScript)

**ปัญหา** — พนักงานควรเห็นยอดทันทีขณะกดสั่งบนแท็บเล็ต แต่ยอดที่ใช้เก็บเงินจริงต้องเชื่อถือได้และมาจากที่เดียว

**ที่เลือก** — เขียนตรรกะเดียวกันไว้ 2 ที่โดยตั้งใจ:

| ที่ | หน้าที่ | ความสำคัญ |
|---|---|---|
| `backend/.../order.calculator.js` | ยอดจริงที่บันทึกและใช้เก็บเงิน | เป็นแหล่งความจริงเสมอ |
| `app/.../bill_calculator.dart` | พรีวิวในตะกร้าก่อนกดยืนยัน | แค่แสดงผล ไม่เคยถูกส่งขึ้นเซิร์ฟเวอร์ |

**ข้อเสียที่ยอมรับ** — โค้ดซ้ำ 2 ภาษา ถ้าแก้กฎต้องแก้ทั้งคู่
จึงมีเทสต์ทั้งสองฝั่งที่ยืนยันด้วย **ตัวเลขชุดเดียวกัน** (180 → 211.86) ถ้าฝั่งใดฝั่งหนึ่งเพี้ยน เทสต์จะจับได้ทันที
และแอปไม่เคยส่งยอดที่คำนวณเองขึ้นไป — ส่งแค่รายการอาหาร เซิร์ฟเวอร์คิดเงินเอง

**ทางเลือกที่ไม่ได้เลือก** — ยิง API ทุกครั้งที่กดเพิ่มของ เพราะ UX แย่ในร้านที่ WiFi ไม่ดี

## 3. ใช้ `Result<T>` ที่เขียนเอง แทน `dartz` / การโยน exception ข้ามชั้น

**ที่เลือก** — sealed class `Result<T>` ที่มี `fold(onSuccess:, onFailure:)`

```dart
result.fold(
  onSuccess: (order) => Get.toNamed(AppRoutes.orderDetail),
  onFailure: (failure) => AppDialogs.error(failure.message),
);
```

**เหตุผล**

- Dart 3 มี sealed class + exhaustive `switch` อยู่แล้ว ไม่จำเป็นต้องพึ่ง dartz
- compiler บังคับให้จัดการทั้งกรณีสำเร็จและล้มเหลว ลืมไม่ได้
- ชื่อ `onSuccess` / `onFailure` อ่านง่ายกว่า `Left` / `Right` สำหรับคนที่ไม่คุ้น FP
- ไม่มี exception หลุดข้ามชั้นไปโผล่กลางหน้าจอ

**ข้อเสียที่ยอมรับ** — ไม่มี `flatMap` / `traverse` แบบ dartz ถ้าโปรเจกต์ใหญ่ขึ้นและมีการต่อ operation เยอะอาจต้องเพิ่มเอง

## 4. รายการอาหารที่ครัวเริ่มทำแล้ว "แก้ไม่ได้"

**ปัญหาจริงในร้าน** — ถ้าพนักงานลดจำนวนหลังครัวลงมือทำไปแล้ว วัตถุดิบเสียฟรีและยอดขายหาย

**ที่เลือก** — ล็อกด้วยสถานะของรายการอาหาร

| สถานะ | แก้จำนวน | ลบ | ยกเลิก (void) |
|---|:---:|:---:|:---:|
| `pending` (ยังไม่เริ่มทำ) | ✅ | ✅ | ✅ ใครก็ได้ |
| `cooking` / `ready` | ❌ | ❌ | ✅ เฉพาะผู้จัดการ |
| `served` | ❌ | ❌ | ❌ |

บังคับทั้งฝั่ง API (คืน 409) และซ่อนปุ่มในแอป — **ฝั่ง API เป็นตัวตัดสิน** ส่วน UI แค่ช่วยไม่ให้กดผิด

---

## 5. โต๊ะหนึ่งเปิดได้ทีละบิล

**ที่เลือก** — สร้างออเดอร์บนโต๊ะที่ยังมีบิลค้างจะได้ HTTP 409 พร้อมข้อความให้ไปเพิ่มรายการในบิลเดิม

**เหตุผล** — กันเคสพนักงาน 2 คนเดินไปโต๊ะเดียวกันแล้วเปิดบิลซ้อน ทำให้ยอดแยกกันและเก็บเงินพลาด

**ข้อเสียที่ยอมรับ** — ยังไม่รองรับ "แยกบิลรายคน" ซึ่งร้านจริงเจอบ่อย บันทึกไว้ในสิ่งที่จะทำต่อแล้ว

## 6. SQLite แทน PostgreSQL

**ที่เลือก** — SQLite ผ่าน `better-sqlite3`

**เหตุผล**

- ร้านอาหาร 1 สาขามี transaction ระดับหลักพันต่อวัน — SQLite รับไหวสบาย
- ผู้ที่มาดูผลงาน `git clone` แล้ว `npm run dev` ได้เลย ไม่ต้องติดตั้ง DB server หรือรัน container
- `better-sqlite3` เป็น synchronous API ทำให้โค้ด repository อ่านง่ายและไม่ต้องจัดการ connection pool
- เปิด WAL mode ให้อ่าน/เขียนพร้อมกันได้จากหลายเครื่องในร้าน

**ข้อเสียที่ยอมรับ** — ขยายเป็นหลายสาขาที่เขียนพร้อมกันหนัก ๆ ไม่ได้
จึงแยกทุก SQL ไว้ในชั้น `repository` เท่านั้น ถ้าจะย้ายไป PostgreSQL แก้ชั้นเดียวจบ ชั้น service ไม่ต้องแตะ

---

## 7. GetX ทั้ง state, DI และ routing

**ที่เลือก** — GetX ตัวเดียวคุมทั้ง 3 อย่าง

**เหตุผล**

- โจทย์ระบุให้ใช้ GetX
- `Bindings` ผูกกับ route ทำให้ controller ถูกสร้างตอนเข้าหน้าและถูกเก็บกวาดตอนออก — จัดการ lifecycle ได้ชัด
- `Get.lazyPut(fenix: true)` ทำให้บัญชีครัวไม่ต้องเสียแรงสร้าง controller ของรายงานที่ไม่มีสิทธิ์เห็น

**ข้อควรระวังที่จัดการแล้ว**

- GetX ทำให้ "เรียกอะไรจากที่ไหนก็ได้" ซึ่งพังโครงสร้างได้ง่าย → บังคับให้ controller รับ dependency ผ่าน constructor เท่านั้น
  ไม่เรียก `Get.find()` กลางไฟล์ ทำให้เทสต์ยัดของปลอมเข้าไปได้ (ดู `cart_controller_test.dart`)
- `Get.snackbar` / `Get.dialog` ถูกรวมไว้ที่ `AppDialogs` ที่เดียว ไม่กระจายทั่วโค้ด

## 8. Demo Mode สลับที่ชั้น data source

**ปัญหา** — อยากให้คนที่มาดูผลงานกดลิงก์เดียวแล้วลองใช้ได้เลย โดยไม่ต้องจ่ายค่าเซิร์ฟเวอร์
และไม่เจอ cold start 30 วินาทีของ free tier

**ที่เลือก** — เขียน data source อีกชุดที่คุยกับ "เซิร์ฟเวอร์จำลอง" ในหน่วยความจำ (`core/demo/`)
แล้วสลับด้วย `--dart-define=DEMO_MODE=true` ที่ `InitialBinding` จุดเดียว

```dart
void _bindDataSources() {
  if (AppConfig.demoMode) {
    _bindDemoDataSources();   // ← สลับที่นี่ที่เดียว
    return;
  }
  ...
}
```

**ผลที่ได้** — deploy ขึ้น GitHub Pages ฟรีถาวร ไม่มีเซิร์ฟเวอร์ ไม่มี cold start
และเป็นตัวพิสูจน์ว่าการแยกชั้นได้ผลจริง เพราะ **หน้าจอ, controller และ use case ไม่ถูกแก้แม้แต่บรรทัดเดียว**

**ข้อเสียที่ยอมรับ** — ข้อมูลหายเมื่อรีเฟรช และไม่มี realtime (ไม่มี socket ให้ต่อ)
ยอมรับได้เพราะเป็นโหมดสำหรับลองใช้เท่านั้น และมีแบนเนอร์บอกผู้ใช้ชัดเจน

## 9. โหลดเมนูทั้งหมดครั้งเดียวแล้วกรองในเครื่อง

**ที่เลือก** — ดึงเมนูทั้งหมด (หลักสิบรายการ) มาเก็บไว้ แล้วกรองหมวดหมู่/ค้นหาในเครื่อง

**เหตุผล** — พนักงานกดสลับหมวดหมู่ถี่มากตอนรับออเดอร์ ถ้ายิง API ทุกครั้งจะหน่วงและกินเน็ตในร้านที่ WiFi ไม่ดี
ส่วนช่องค้นหาก็หน่วง 250ms ก่อนกรอง เพื่อไม่ให้ rebuild ทุกตัวอักษร

**ข้อเสียที่ยอมรับ** — ถ้าร้านมีเมนูหลักพันรายการต้องเปลี่ยนไปใช้ pagination
ซึ่ง API รองรับอยู่แล้ว (`?page=&limit=`) แค่ยังไม่ได้ใช้ฝั่งแอป

## 10. เขียนกราฟเองแทนใช้ package

**ที่เลือก** — กราฟแท่งรายชั่วโมงและแถบสัดส่วนเขียนด้วย widget พื้นฐานของ Flutter

**เหตุผล**

- ต้องการแค่กราฟแท่งเรียบ ๆ 2 แบบ การลง `fl_chart` เพิ่ม ~300KB เพื่อใช้ 5% ของความสามารถไม่คุ้ม
- คุมสีและมุมโค้งให้เข้ากับธีมได้เป๊ะโดยไม่ต้องสู้กับ API ของ package
- ลด dependency ที่ต้องตามอัปเดตในระยะยาว

**ข้อเสียที่ยอมรับ** — ถ้าต้องการกราฟซับซ้อน (เส้นหลายชุด, zoom, tooltip ขั้นสูง) ควรเปลี่ยนไปใช้ package

## 11. พิมพ์ใบเสร็จผ่านเครื่องพิมพ์ความร้อนจริง — เจาะจงแค่ LAN/WiFi ก่อน (ไม่ใช่ Bluetooth/USB)

> อัปเดต: เดิมข้อนี้เคยตัดสินใจไม่ต่อเครื่องพิมพ์จริงเลย (เดโมพอร์ตโฟลิโอ ไม่ใช่ระบบขายจริง)
> ภายหลังพบว่าเป็น blocker จริงสำหรับการใช้งานหน้าร้าน (ดู `docs/FEATURE-GAP-ANALYSIS.md`
> #3 และ `docs/tickets/03-receipt-printer.md`) จึงทำเพิ่ม แต่ยังเจาะจงขอบเขตตามด้านล่าง

**ที่เลือก** — พิมพ์ใบเสร็จจริงผ่าน ESC/POS โดยส่งคำสั่งเป็น raw bytes ผ่าน TCP socket ไปยัง
เครื่องพิมพ์ความร้อนบนวง LAN/WiFi เดียวกัน (พอร์ต 9100 ซึ่งเป็นค่ามาตรฐานของเครื่องพิมพ์เกือบทุก
ยี่ห้อ) — ตั้งค่า IP/พอร์ต/ขนาดกระดาษได้จากหน้าตั้งค่า ผูกกับเครื่อง cashier นั้น ๆ ไม่ผูกกับร้าน
ยังไม่รองรับ Bluetooth หรือ USB

**เหตุผล** — เครื่องพิมพ์ความร้อนที่ร้านอาหารไทยใช้ทั่วไป (Xprinter, Gprinter, HPRT ฯลฯ) รองรับ
raw ESC/POS ผ่าน WiFi/Ethernet เป็นมาตรฐานอยู่แล้ว ทำให้เชื่อมต่อได้โดยไม่ต้องพึ่ง native plugin
สำหรับจับคู่ Bluetooth (ต้องขอ permission เพิ่มทั้ง Android/iOS และมีโค้ด platform channel ที่
ทดสอบได้เฉพาะบนอุปกรณ์จริงเท่านั้น) — สภาพแวดล้อมพัฒนานี้ไม่มีฮาร์ดแวร์เครื่องพิมพ์หรืออุปกรณ์
Bluetooth จริงให้ทดสอบ จึงจำกัดขอบเขตไว้ที่ทางที่ตรวจสอบได้แน่ใจว่าถูกต้องก่อน
(ยืนยันด้วยเทสต์ของตาราง CP874/ESC-POS bytes และรันจริงในเว็บว่า fallback ทำงานถูกต้อง)

ข้อความไทยเข้ารหัสเองด้วยตาราง CP874/TIS-620 (`Cp874Codec`) เพราะไลบรารี `esc_pos_utils_plus`
ที่ใช้สร้างคำสั่ง ESC/POS รองรับแค่ `latin1`/GBK ไม่มี codec ภาษาไทยมาให้

เว็บเปิด TCP socket ตรง ๆ จาก browser ไม่ได้ (ไม่มี `dart:io`) จึงคืนข้อความแจ้งให้ใช้ใบเสร็จ
บนจอแทนทันทีเมื่อกดพิมพ์ ไม่กระทบ demo mode หรือแพลตฟอร์มที่ยังไม่รองรับ

**ข้อเสียที่ยอมรับ** — เครื่องพิมพ์ที่ต่อผ่าน Bluetooth/USB เท่านั้น (ไม่มี WiFi/Ethernet)
ยังใช้กับฟีเจอร์นี้ไม่ได้ ถ้าจะเพิ่มต้องต่อ native plugin ใหม่ (เช่น `esc_pos_bluetooth`) และ
ต้องมีอุปกรณ์จริงมาเทสต์ — สถาปัตยกรรมรองรับอยู่แล้วเพราะเทมเพลตใบเสร็จ (`ReceiptTicketBuilder`)
แยกจากชั้นส่งข้อมูล (`printer_transport_io.dart`) ไว้ตั้งแต่แรก เปลี่ยน/เพิ่ม transport ได้โดยไม่
ต้องแตะ logic การสร้างใบเสร็จ

## 12. ใช้ SQLite ต่อไป ไม่ย้ายไป PostgreSQL แม้รองรับหลายสาขาได้ดีกว่า

**ที่เลือก** — คงสถาปัตยกรรมสาขาเดียว (single-tenant, single-database) ไว้ตามสโคปเดิมของโปรเจกต์

**เหตุผล** — เป้าหมายของโปรเจกต์คือร้านอาหารสาขาเดียว การรองรับหลายสาขาต้องออกแบบเพิ่ม
(tenant isolation, sync ข้าม branch, aggregate reporting ข้ามสาขา) ซึ่งเป็นงานออกแบบระดับใหญ่
ที่ไม่ได้อยู่ในสโคปที่ต้องการนำเสนอตอนนี้ — ทำไปก็จะเพิ่มความซับซ้อนโดยไม่ได้ใช้จริง

**ข้อเสียที่ยอมรับ** — ถ้าลูกค้าต้องการหลายสาขาในอนาคต ต้องออกแบบ multi-tenancy เพิ่มเติม
แต่ชั้น repository ที่แยกไว้แล้ว (ดูข้อ 6) ทำให้เปลี่ยนฐานข้อมูลจาก SQLite ไป PostgreSQL
ได้โดยไม่ต้องแตะ service/controller layer

## 13. Offline mode — เจาะจงแค่ "สั่งเพิ่มเข้าออเดอร์เดิม" เท่านั้น

**ที่เลือก** — action เดียวที่ทำงานแบบ offline-first (queue ในเครื่องแล้ว sync อัตโนมัติเมื่อ
เน็ตกลับมา) คือ **สั่งเพิ่มรายการอาหารเข้าออเดอร์ที่เปิดอยู่แล้ว** (`CartController.submit()`
เมื่อ `isAddingToExistingOrder == true`) เท่านั้น เก็บคิวด้วย `get_storage` ผ่าน
`OfflineOrderQueueService` แสดงจำนวนรายการค้าง sync เป็น badge บน AppBar ของทุกหน้า (ต่อยอด
จากไฟบอกสถานะ socket ที่มีอยู่แล้ว) ตรวจจับ "ออฟไลน์" จาก `NetworkFailure` ที่โยนมาจาก
`ApiClient` เมื่อ HTTP call ล้มเหลวจริง (connection error/timeout) ไม่ใช้ปลั๊กอินตรวจสถานะ
เครือข่ายของ OS (เช่น `connectivity_plus`)

**Action ที่ยังไม่รองรับ offline โดยตั้งใจ (ต้องออนไลน์เสมอ):**
- เปิดออเดอร์ใหม่ (`CreateOrderUseCase`) — เสี่ยง conflict สูงกว่า (จองโต๊ะซ้ำ, เลขที่ออเดอร์
  ต้องมาจากเซิร์ฟเวอร์)
- ชำระเงิน/คืนเงิน (`PayOrderUseCase`, refund) และ เปิด/ปิดกะ — ต้องถูกต้องแม่นยำเรื่องเงินเสมอ
  ห้ามมีโอกาส apply ซ้ำหรือ double-count จากการ retry
- ย้ายโต๊ะ/รวมบิล/แยกบิล/ยกเลิกออเดอร์/ส่วนลด — แก้ไข state ของออเดอร์ที่อาจถูกฝั่งอื่นแก้พร้อมกัน
  ระหว่างออฟไลน์ ความเสี่ยง conflict สูง
- จัดการเมนู/พนักงาน/ตั้งค่าร้าน — ไม่ใช่ operation เร่งด่วนระดับหน้าร้าน รอเน็ตกลับมาได้

**เหตุผล** — ตามคำแนะนำใน `docs/tickets/04-offline-mode.md`: เริ่มจาก action ที่ความเสี่ยง
conflict ต่ำสุดก่อน สั่งเพิ่มเข้าออเดอร์ที่เปิดอยู่แล้วแทบไม่มีทางชนกับ state อื่นเพราะแค่ "เพิ่ม
รายการต่อท้าย" ไม่ได้แก้ไขข้อมูลเดิม ต่างจากเปิดออเดอร์ใหม่/ชำระเงินที่ผลลัพธ์ผูกกับสถานะ ณ
ขณะนั้นบนเซิร์ฟเวอร์โดยตรง หากรายการที่ queue ไว้ sync ไม่สำเร็จเพราะเหตุผลอื่นที่ไม่ใช่เน็ตหลุด
(เช่นออเดอร์ถูกปิด/ลบไปแล้วระหว่างที่ออฟไลน์) ระบบจะตัดรายการนั้นออกจากคิวทันทีแทนที่จะ retry
วนไม่รู้จบ แล้วบันทึกข้อความไว้แจ้งผู้ใช้ (`lastFailureMessage`)

**ข้อเสียที่ยอมรับ** — พนักงานยังเปิดออเดอร์ใหม่/รับชำระเงินไม่ได้ตอนเน็ตหลุด ถ้าจะขยายขอบเขต
ต้องออกแบบเพิ่ม (เช่นเลขที่ออเดอร์ชั่วคราวที่เครื่อง + เปลี่ยนเป็นเลขจริงตอน sync, ล็อกการรับชำระ
ซ้ำระหว่าง sync) ซึ่งซับซ้อนกว่ามากและมีความเสี่ยงเรื่องเงินโดยตรง — การตรวจจับออฟไลน์ด้วย
`NetworkFailure` (reactive, หลัง API call ล้มเหลวจริง) ก็ตรวจจับได้ช้ากว่าปลั๊กอินตรวจสถานะ
เครือข่ายของ OS (proactive) เล็กน้อย แต่ไม่ต้องพึ่ง native permission และทดสอบได้เต็มรูปแบบด้วย
unit test ล้วน ๆ

## 14. Promotion engine — ไม่ซ้อนโปรโมชันหลายใบ, รวมกับส่วนลดมือได้แต่ไม่เกิน subtotal, auto-match ประเมินใหม่ทุกครั้ง

**ปัญหา** — ต้องเพิ่มส่วนลดแบบตั้งเงื่อนไขล่วงหน้า (happy hour, โค้ดส่วนลด, ซื้อ 1 แถม 1) โดยห้าม
กระทบลำดับการคำนวณเดิม (`subtotal → discount → service charge → VAT`, ดูข้อ 2) และห้ามทำให้
`order.calculator.js`/`bill_calculator.dart` ซับซ้อนเกินจำเป็น

**ที่เลือก**

- **สูงสุด 1 โปรโมชันต่อบิลเสมอ** ไม่ว่าจะ auto-match หรือกรอกโค้ด — เลี่ยงความซับซ้อนของการจัดลำดับ/
  รวมหลายโปรโมชันพร้อมกันในเวอร์ชันแรก ตรรกะจับคู่ทั้งหมดแยกไว้ที่ `promotion.engine.js`
  (ฟังก์ชันบริสุทธิ์ทั้งหมด) ไม่ปนกับ `calculateBill` ที่รับแค่ `promotionDiscountAmount` ไปรวม
- **ส่วนลดโปรโมชัน "รวมกับ" ส่วนลดมือได้** (ไม่ใช่เลือกอย่างใดอย่างหนึ่ง) แต่ผลรวมทั้งคู่ต้องไม่เกิน
  subtotal — สะท้อนพฤติกรรมจริงของร้าน (แคชเชียร์อาจลดให้ลูกค้าประจำเพิ่มเติมนอกเหนือจากโปรโมชันที่มีอยู่แล้ว)
- **โปรโมชันแบบ auto (ไม่มีโค้ด) ถูกประเมินใหม่ทุกครั้งที่คำนวณบิล** (`recalculate()`) เลือกตัวที่ให้
  ส่วนลดมากที่สุดในบรรดาที่เข้าเงื่อนไข ณ ขณะนั้น — ถ้าลูกค้ากรอกโค้ดไว้ (`promotion_code_snapshot`
  ไม่เป็น null) จะ "ยึด" โค้ดนั้นไว้เป็นหลักจนกว่าจะไม่เข้าเงื่อนไขอีกต่อไปหรือถูกลบออกเอง แม้ auto
  promotion อื่นจะให้ส่วนลดมากกว่าก็ตาม — ป้องกันไม่ให้ระบบ "แย่ง" เปลี่ยนโปรโมชันที่ลูกค้าตั้งใจใช้เอง
- **ลบโปรโมชันออกจากออเดอร์ (`DELETE /orders/:id/promotion`) ไม่ได้แปลว่า "ห้ามใช้โปรโมชันอีก"** —
  เป็นแค่การเคลียร์โค้ดที่ผูกไว้ ถ้ายังมี auto promotion ที่เข้าเงื่อนไขอยู่ ระบบจะใส่กลับให้ทันทีตอน
  คำนวณครั้งถัดไป (เหมือน VAT/Service Charge ที่คำนวณจาก settings ปัจจุบันเสมอ ไม่ใช่ค่าที่ "ล็อก" ไว้)
- **BOGO** คำนวณด้วยการกระจายราคาเป็น "ราคาต่อชิ้น" ของทุกรายการที่เข้าเงื่อนไข (ข้ามเมนูได้) เรียง
  ถูกไปแพง แล้วให้ครึ่งที่ถูกกว่าฟรี (`floor(count/2)` ชิ้น) — ง่ายกว่าการจับคู่ "ซื้อเมนู A แถมเมนู A"
  ตรง ๆ และให้ผลลัพธ์ที่ยุติธรรมกับลูกค้าเมื่อซื้อเมนูราคาต่างกันในโปรโมชันเดียว
- **โปรโมชันที่ใช้ไปแล้วถูก snapshot ไว้ที่ออเดอร์** (`promotion_name_snapshot`,
  `promotion_code_snapshot`) แยกจาก `promotion_id` (FK แบบ `ON DELETE SET NULL`) — ลบโปรโมชันทิ้งจาก
  ระบบภายหลังจะไม่ทำให้ออเดอร์เก่าที่เคยใช้โปรโมชันนั้นแสดงข้อมูลหายหรือพัง

**ข้อเสียที่ยอมรับ** — ร้านที่อยากให้ลูกค้าใช้โปรโมชันซ้อนกันหลายใบพร้อมกัน (เช่น โค้ดส่วนลด + happy
hour พร้อมกัน) ทำไม่ได้ในเวอร์ชันนี้ ต้องเลือกใช้ได้ทีละ 1 ใบ — ถ้าจะรองรับต้องออกแบบลำดับความสำคัญ/
กติกาการรวมโปรโมชันหลายใบเพิ่ม ซึ่งซับซ้อนขึ้นมากและเสี่ยงสร้างส่วนลดที่ร้านไม่ได้ตั้งใจให้

## 15. Inventory/Stock — หน่วยอิสระไม่แปลงข้ามหน่วย, ตัดสต๊อกตอนส่งครัว, ผูกวัตถุดิบฝังในเมนู

**ปัญหา** — ต้องเพิ่มระบบตัดสต๊อกวัตถุดิบอัตโนมัติเมื่อขาย (ดู `docs/tickets/06-inventory-stock.md`)
โดยห้ามกระทบ flow การสั่งอาหาร/ครัวเดิม และต้องตัดสินใจหลายจุดที่ ticket ไม่ได้ระบุไว้ชัดเจน
(หน่วยนับ, จังหวะตัดสต๊อกที่แน่นอน, การคืนสต๊อกเมื่อยกเลิก, รายการที่สั่งเพิ่มหลังส่งครัวไปแล้ว)

**ที่เลือก**

- **หน่วย (`unit`) เป็น string อิสระที่ร้านตั้งเอง** เช่น "กก.", "กรัม", "ฟอง", "ตัว" — ไม่มี unit
  conversion ข้ามหน่วย (เช่น กก. ↔ กรัม) ในเวอร์ชันแรก ร้านต้องตั้งหน่วยของวัตถุดิบกับ `qtyPerUnit`
  ของเมนูให้เป็นหน่วยเดียวกันเอง — เลี่ยงความซับซ้อนของตาราง conversion/หน่วยมาตรฐานที่ไม่จำเป็นสำหรับ
  ร้านอาหารขนาดเล็ก-กลางที่เป็นกลุ่มเป้าหมาย
- **ตัดสต๊อกตอน "ส่งครัว" (`sendToKitchen`) ไม่ใช่ตอนสั่ง/ตอนจ่ายเงิน** — ตรงกับคำว่า "ยืนยัน/ส่งครัว"
  ใน ticket มากที่สุด และเป็นจุดที่ครัวเริ่มลงมือทำจริง (ก่อนหน้านั้นลูกค้ายังแก้ไข/ยกเลิกได้อิสระโดยไม่
  กระทบสต๊อกจริง) รายการที่เพิ่มเข้าออเดอร์ที่ถูกส่งครัวไปแล้วจะถูกตัดสต๊อกทันทีที่เพิ่ม (ไม่ต้องกด
  "ส่งครัว" ซ้ำ) ส่วน `sendToKitchen` เองออกแบบให้ idempotent — เรียกซ้ำได้โดยตัดสต๊อกเฉพาะรายการที่ยัง
  ไม่เคยถูกตัด (`order_items.stock_deducted`)
- **ยกเลิกรายการ/ทั้งบิลคืนสต๊อกอัตโนมัติเสมอ** ถ้ารายการนั้นเคยถูกตัดสต๊อกไปแล้ว (ทั้งยกเลิกรายการเดี่ยว,
  ลบรายการ, แก้จำนวน (ปรับตามส่วนต่างเท่านั้น ไม่ตัดใหม่ทั้งหมด), และยกเลิกทั้งบิล) — สะท้อนว่าวัตถุดิบ
  ยังไม่ถูกใช้จริงถ้าไม่ได้เสิร์ฟลูกค้า
- **`order_items.stock_deducted`** (boolean) ทำให้การตัด/คืนสต๊อกเป็น idempotent และแยกแยะได้ว่ารายการ
  ไหน "ตัดไปแล้วต้องคืนตอนยกเลิก" กับรายการที่ยังไม่เคยตัด (เช่นถูกยกเลิกตั้งแต่ยังเป็น pending ก่อนส่งครัว)
- **`menu_items.auto_disabled_by_stock`** (boolean) แยก "ระบบปิดขายเองเพราะสต๊อกหมด" ออกจาก "พนักงานปิด
  ขายเอง" (สินค้าหมดจริงที่ไม่เกี่ยวกับสต๊อกในระบบ, หรือของไม่อร่อยวันนี้เลยงดขาย) — เติมสต๊อกกลับจะเปิด
  ขายอัตโนมัติให้เฉพาะเมนูที่ระบบเป็นคนปิดเท่านั้น การแก้ไขเมนูที่แตะ `isAvailable` (ฟอร์มแก้เมนู หรือปุ่ม
  เปิด/ปิดขายโดยตรง) ถือเป็นการ override เจตนาของพนักงานเสมอ ระบบจะไม่ auto-เปิดขายทับให้ภายหลัง
- **ผูกวัตถุดิบฝังอยู่ในฟอร์ม/payload สร้าง-แก้ไขเมนู** (`ingredients: [{ingredientId, qtyPerUnit}]`)
  แทนที่จะแยก endpoint/หน้าจอผูกต่างหาก — mirror ทุกจุดกับวิธีที่ `optionGroups` ถูกจัดการอยู่แล้ว (แทนที่
  ทั้งชุดทุกครั้งที่บันทึกเมนู) ลด API surface และนำ pattern ที่พิสูจน์แล้วมาใช้ซ้ำ
- **ค่าที่เกี่ยวกับสต๊อก (`current_stock`, `low_stock_threshold`, `qty_per_unit`) เก็บเป็น `REAL` ตรง ๆ
  ไม่ผ่าน `toSatang`/`toBaht`** (ดูข้อ 1) เพราะไม่ใช่หน่วยเงิน — ความคลาดเคลื่อนทศนิยมเล็กน้อยของสต๊อก
  ยอมรับได้ ต่างจากเงินที่ต้องเป๊ะเสมอ

**ข้อเสียที่ยอมรับ** — ร้านที่ต้องการแปลงหน่วยข้ามกัน (เช่น ซื้อวัตถุดิบเป็น กก. แต่ใช้ต่อเมนูเป็นกรัม)
ต้องตั้งหน่วยให้ตรงกันเองตั้งแต่แรก (ป้อนวัตถุดิบเป็น "กรัม" แทน "กก." ถ้าเมนูใช้หน่วยกรัม) และยังไม่มี
หน้ารายงานการใช้วัตถุดิบ (ingredient usage report) ตามที่ระบุไว้ในขอบเขตงานของ ticket — เพราะไม่ได้อยู่ใน
Acceptance Criteria ทั้ง 4 ข้อ จึงเลื่อนไปทำเป็น ticket แยกในอนาคตถ้าร้านต้องการจริง

## 16. ใบเสร็จแสดง "เงินที่ลูกค้ายื่นมา" ไม่ใช่ยอดที่ตัดเข้าบิล

**ปัญหา** — `payments` เก็บทั้ง `amount` (ยอดที่ตัดเข้าบิล) และ `received` (เงินที่ลูกค้ายื่นมา)
แต่ใบเสร็จเดิมแสดง `amount` คู่กับบรรทัดเงินทอน ทำให้ตัวเลขบนใบเสร็จกระทบยอดกันเองไม่ได้ —
ลูกค้าจ่ายเงินสด 227.20 แต่ใบเสร็จเขียน "เงินสด 207.20" คู่กับ "เงินทอน 20.00" ซึ่งไม่ตรงกับ
เงินที่ยื่นให้จริง

**ที่เลือก** — เพิ่ม getter `Payment.tendered` ไว้ที่ entity **ที่เดียว** แล้วให้ทั้งใบเสร็จบนจอ
(`receipt_page.dart`) และใบเสร็จที่พิมพ์ออกเครื่องพิมพ์ความร้อน (`receipt_ticket_builder.dart`)
เรียกใช้ร่วมกัน ใบเสร็จจึงกระทบยอดได้ตามธรรมเนียมใบเสร็จไทย: **ยื่นมา − ทอน = ยอดที่ตัดเข้าบิล**

```dart
double get tendered => received > amount ? received : amount;
```

เงื่อนไข `>` เผื่อข้อมูลเก่าที่ยังไม่มีช่อง `received` (ได้ 0) ให้ถอยไปใช้ `amount` ตามเดิม
ส่วน QR/บัตร/โอน ไม่มีการทอน ทั้ง backend และ demo store เซ็ต `received = amount` อยู่แล้ว
จึงไม่มีอะไรเปลี่ยน

**จุดที่จงใจไม่เปลี่ยน** — ยังใช้ `amount` ตามเดิมสองที่:

- `ReceiptController.refundableAmount` — คืนเงินได้แค่ยอดที่ตัดเข้าบิลจริง ถ้าใช้ `tendered`
  จะคืนเกินเป็นจำนวนเท่ากับเงินทอน
- รายการ "จ่ายแล้ว" ในหน้าเก็บเงิน — เป็นมุมมองยอดคงเหลือ ผลรวมต้องเท่ายอดบิลพอดี

**เหตุผลที่รวมไว้ที่ entity ไม่ใช่แก้ทีละหน้า** — ใบเสร็จบนจอกับใบเสร็จที่พิมพ์เป็นคนละไฟล์และ
เคยเขียนแยกกัน ถ้าแก้ทีละจุดจะเพี้ยนออกจากกันภายหลังโดยไม่มีอะไรฟ้อง เพราะไม่มีใครเปิดเทียบสองที่พร้อมกัน

**ข้อเสียที่ยอมรับ** — ผลรวมของบรรทัดวิธีชำระเงินบนใบเสร็จจะมากกว่ายอดบิลเท่ากับเงินทอน
ซึ่งถูกต้องตามธรรมเนียมใบเสร็จ แต่ต่างจากมุมมองทางบัญชีที่ผลรวมต้องเท่ายอดบิลพอดี —
ระบบจึงแยกสองมุมมองนี้ออกจากกันชัดเจนตามรายการด้านบน

## 17. AppClock — รวมการอ่านเวลาปัจจุบันไว้ที่เดียว เพื่อให้ภาพหน้าจอถ่ายซ้ำได้ผลเหมือนเดิม

**ปัญหา** — ภาพหน้าจอในเอกสารถูกถ่ายด้วย golden test แล้วคอมมิตลง git แต่โค้ดที่ผลลัพธ์บนจอ
ขึ้นกับเวลาปัจจุบันเรียก `DateTime.now()` ตรง ๆ ภาพ 4–6 ภาพจึงได้ไฟล์ไม่เหมือนเดิมทุกครั้งที่ถ่าย
(ต่างกันแค่ `· 07:45` เป็น `· 07:54`) เวลาดูประวัติใน git จึงแยกไม่ออกว่าภาพไหนเปลี่ยนเพราะ UI
เปลี่ยนจริง ภาพไหนแค่นาฬิกาเดิน

**ที่เลือก** — เพิ่ม `AppClock` เป็นทางผ่านเดียวของเวลาปัจจุบัน ค่าเริ่มต้นคือนาฬิกาจริง
แต่ `freeze()` ได้ในเทสต์และสคริปต์ถ่ายภาพ แล้วไล่เปลี่ยนจุดที่ผลลัพธ์บนจอขึ้นกับเวลาให้เรียกผ่าน
`AppClock` (demo store, seed ยอดขายย้อนหลัง, `Formatters.elapsed`, ตัวกรองออเดอร์วันนี้,
คำทักทายตามช่วงเวลา, ช่วงเวลาของรายงาน, promotion engine, เวลาเข้าคิวออเดอร์ออฟไลน์, date picker)

สคริปต์ถ่ายภาพตรึงเวลาไว้ที่ **11 ก.ย. 2026 19:42** ก่อน seed ข้อมูลสาธิต และคืนนาฬิกาจริงใน
`tearDownAll`

**ทำไมตรึงเป็นเวลา "ตามเครื่อง" ไม่ใช่ UTC** — `Formatters.parse` แปลง UTC กลับเป็นเวลาเครื่อง
ก่อนแสดงผลอยู่แล้ว พอตรึงเป็นเวลาเครื่อง ค่าที่ round-trip ออกมาจึงเท่ากันทุกเครื่องไม่ว่า time zone
จะตั้งไว้เป็นอะไร ถ้าตรึงเป็น UTC คนที่รันในไทย (UTC+7) จะได้ภาพเลื่อนไป 7 ชั่วโมง

**จุดที่จงใจไม่ตรึง** — id ของคิวออเดอร์ออฟไลน์ยังใช้ `DateTime.now()` เพราะต้องไม่ซ้ำ
ถ้าใช้เวลาที่ตรึงไว้ ทุกรายการที่เข้าคิวจะได้ id เดียวกันหมด (ปิดกฎ lint เป็นบรรทัดพร้อมเหตุผลกำกับ)

**บั๊กที่เจอระหว่างทาง** — ตรึงในแอปจนหมดแล้วจอครัวยังดิ้นอยู่ 2 ภาพ ไล่ดูพบว่าตัวสคริปต์ถ่ายภาพเอง
ยังย้อนเวลาตั๋วด้วยนาฬิกาจริงขณะที่ "ตอนนี้" ถูกตรึงไว้แล้ว ตั๋วทุกใบจึงขึ้น "11 ชม. 56 นาที"
เหมือนกันหมดและติดแถบเตือนของช้าสีแดงหมดทุกใบ — แก้แล้วขึ้น 18 / 4 / 2 นาทีตามที่ตั้งใจไว้

**ผลที่ได้นอกจากความเรียบร้อยของ git** — เมื่อภาพนิ่งแล้ว ภาพที่ขยับใน diff ย่อมแปลว่า UI
เปลี่ยนจริงเสมอ การถ่ายภาพจึงกลายเป็นเครื่องมือตรวจจับการเปลี่ยนแปลงที่ไม่ตั้งใจไปด้วย

**บังคับด้วย lint** — กฎ `use_app_clock_not_date_time_now` ดัก `DateTime.now()` /
`DateTime.timestamp()` ที่เรียกตรง ๆ ครอบคลุมทั้ง `lib/**` และ `tool/screenshots/**`
(ดู `app/tool/lints/README.md`) เพราะบั๊กที่เจ็บที่สุดอยู่ในตัวสคริปต์ถ่ายภาพเอง ไม่ใช่ในโค้ดแอป

## 18. โหมดคอนทราสต์สูง — พาเลตต์เดิมที่เข้มขึ้น ไม่ใช่ธีมที่สอง

**ปัญหา** — R-06 จากผลตรวจ UI/UX ค้างมาตั้งแต่รอบที่ 2 แอปล็อกโหมดสว่างอย่างเดียว แต่หน้างานจริง
ของร้านอาหารกินคอนทราสต์ไปอีกชั้นหนึ่งจากที่วัดได้บนจอสะอาดในร่ม: จอครัวโดนไอน้ำ โต๊ะริมหน้าต่าง
โดนแดดตอนกลางวัน และแท็บเล็ตรับออเดอร์มีรอยนิ้วมือตลอดเวลา

**ที่เลือก — คอนทราสต์สูง ไม่ใช่ dark mode** ร้านอาหารได้ประโยชน์จากการอ่านออกกลางแดดมากกว่า
การถนอมสายตาตอนกลางคืน และ dark mode ต้องนิยาม token ใหม่ทั้งหมดพร้อมตรวจคอนทราสต์ใหม่ทุกคู่สี
ขณะที่คอนทราสต์สูงต่อยอดจากพาเลตต์เดิมได้ตรง ๆ

**โครงสีไม่เปลี่ยน เปลี่ยนแค่ความเข้ม** — ส้มยังเป็นแบรนด์ เหลืองยังแปลว่ามีลูกค้า แดงยังแปลว่า
อันตราย พนักงานที่ชินกับสีอยู่แล้วจึงไม่ต้องเรียนรู้ใหม่ และไม่ต้องดูแลภาษาสีสองชุดคู่ขนาน

ตัวเลขด้านล่างเป็น **ค่าต่ำสุดเมื่อเทียบกับทุกพื้นที่ถูกใช้จริง** (surface, background,
surfaceAlt, primarySoft, secondarySoft) ไม่ใช่ค่าบนพื้นขาวอย่างเดียว — ดูหัวข้อ "บั๊กที่เจอ
ระหว่างทำ" ด้านล่างว่าทำไมถึงต้องวัดแบบนี้

| token | ปกติ | คอนทราสต์สูง |
|---|---|---|
| textPrimary | 15.08:1 | 21.00:1 |
| textSecondary | 4.67:1 | 11.48:1 |
| textDisabled | 2.26:1 | 6.92:1 |
| brandInk / warningInk / successInk | 4.62 / 4.95 / 5.11 | 7.45 / 7.75 / 8.42 |
| secondaryInk / dangerInk / purpleInk / infoInk | 4.75 / 4.87 / 6.55 / 5.42 | 7.90 / 7.66 / 9.96 / 8.02 |
| border | 1.24:1 | 4.10:1 |

`textDisabled` จงใจไม่ดันถึง AAA เพราะหน้าที่ของมันคือ "ดูไม่พร้อมใช้งาน" ถ้าเข้มเท่าข้อความ
ปกติจะแยกไม่ออก — WCAG ก็ยกเว้นองค์ประกอบที่ปิดใช้งานไว้อยู่แล้ว

ตัวหนังสือทุกตัวขยับจากเกณฑ์ AA (4.5:1) เป็น AAA (7:1) ส่วนขอบการ์ดผ่านเกณฑ์องค์ประกอบที่ไม่ใช่
ตัวหนังสือ (3:1) ซึ่งโหมดปกติไม่ผ่าน — โหมดปกติตั้งใจให้ขอบจางเพื่อให้การ์ดดูลอย แต่กลางแดดจ้า
ขอบจาง ๆ หายไปเลยจนแยกไม่ออกว่าการ์ดไหนจบตรงไหน

**ที่เก็บสถานะ — เป็น static บน `AppColors` ไม่ได้ส่งผ่าน BuildContext** ทั้งแอปเรียก
`AppColors.x` ตรง ๆ 396 จุดใน 43 ไฟล์ การเปลี่ยนทุกจุดให้อ่านผ่าน `Theme.of(context)` เป็นการรื้อ
ที่ไม่คุ้มกับสิ่งที่ได้ และเสี่ยงพลาดเงียบ ๆ ตรงจุดที่ลืมแก้ วิธีนี้แลกมาด้วยการที่ token ที่เปลี่ยนตามโหมด
ต้องเป็น getter ไม่ใช่ `const` จึงต้องถอด `const` ออกจากจุดที่ใช้ token พวกนี้ 104 จุด — คอมไพเลอร์
ชี้ให้ทุกจุดเอง ไม่มีอะไรพลาดเงียบได้

**กับดักที่เจอตอนทำ** — `AppTheme._textTheme` เป็น `static const` อยู่เดิม พอถอด `const` ออกมันกลาย
เป็น static field ที่คำนวณครั้งเดียวตอนคลาสถูกโหลด สีตัวหนังสือของธีมจึงค้างเป็นของโหมดแรกที่เปิด
แก้โดยเปลี่ยนเป็น getter การสลับโหมดจึงต้องทำสองอย่างคู่กัน: `Get.changeTheme()` สำหรับสีที่ไหล
ผ่านธีม และ `Get.forceAppUpdate()` สำหรับสีที่อ่านจาก `AppColors` ตรง ๆ ซึ่งเป็นส่วนใหญ่ของแอป

**ที่วางปุ่ม — หน้า "บัญชี" ไม่ใช่หน้า "ตั้งค่า"** ด้วยเหตุผลเดียวกับตัวสลับภาษาใน F-07:
คนที่ต้องใช้จริงคือพนักงานครัวกับพนักงานเสิร์ฟ ซึ่งเข้าหน้าตั้งค่าของแอดมินไม่ได้เลย

**จำค่าไว้กับเครื่อง ไม่ใช่กับบัญชีผู้ใช้** เหมือนภาษาและเครื่องพิมพ์ — แท็บเล็ตหน้าร้านที่โดนแดด
ควรตั้งคอนทราสต์สูงค้างไว้ ไม่ว่าใครจะมาล็อกอิน

**บั๊กที่เจอระหว่างทำ — วัดคอนทราสต์บนพื้นขาวอย่างเดียวทำให้รายงานเกินจริง**

เทสต์ชุดแรกเทียบ ink กับ `AppColors.surface` (ขาว) อย่างเดียวจึงผ่านหมด ทั้งที่ของจริงหลายที่
วางบนพื้นเทาอ่อนหรือพื้น soft ของสีตัวเอง ซึ่งกินคอนทราสต์ไปอีก 0.5–1.5 จุด พอแก้เทสต์ให้ไล่
เทียบทุกพื้นก็พบว่า **พาเลตต์เดิมที่เคยประกาศว่า "ผ่าน AA ครบ" จริง ๆ แล้วตก 3 ตัว**:
`textSecondary` (4.31) `warningInk` (4.48) และ `infoInk` (4.48) เมื่อไปวางบน `surfaceAlt`
— ปรับค่าทั้งสามแล้ว และคอมเมนต์เดิมใน `app_colors.dart` ที่อ้างว่าตรวจครบแล้วก็แก้ให้ตรงความจริง

ยังเจออีกชั้นว่า **สีสดที่เอาไปเป็นพื้นปุ่มก็ตกเกณฑ์เหมือนกัน** — ปุ่มเดินสถานะในจอครัวใช้ป้าย
สีขาวบนสีเหลือง "รอทำ" ได้แค่ 2.13:1 และปุ่ม "รับชำระ" สีเขียวได้ 3.45:1 ทั้งที่เป็นปุ่มรับเงิน
แก้โดยใช้เฉด ink เป็นพื้นปุ่มเหมือนที่ทำกับชิป และเพิ่มเทสต์บังคับว่าสีที่เอาไปเป็นพื้นปุ่ม/ชิป
ต้องรองป้ายสีขาวได้ 4.5:1 เสมอ

**ชั้นที่สาม — สีสดถูกใช้เป็นตัวหนังสือ/ไอคอนอยู่ 39 จุดทั่วแอป**

ไล่ตรวจซ้ำอีกรอบด้วยการแยกประเภทการใช้งานทุกจุดที่อ้างถึงสีสด (ตัวหนังสือ / ไอคอน /
ป้ายปุ่ม / พื้น-จุด-ขอบ) แล้ววัดกับเกณฑ์ของแต่ละประเภท (ตัวหนังสือ 4.5:1, ไอคอน 3:1)
พบว่าเมื่อเทียบกับพื้นที่เข้มที่สุดที่ใช้จริง **สีสดไม่มีตัวไหนผ่านเกณฑ์ตัวหนังสือเลย
ยกเว้นม่วง** และสามสี (ส้ม 2.53 / เหลือง 1.90 / เขียวมิ้นต์ 2.28) ไม่ผ่านแม้แต่เกณฑ์ไอคอน

จุดที่เจ็บที่สุดคือหัวคอลัมน์จอครัว ซึ่งวางตัวหนังสือสีสดบนพื้น tint ของสีตัวเอง —
"รอทำ" ได้แค่ **1.94:1** ทั้งที่เป็นป้ายบอกสถานะหลักของจอที่ครัวต้องอ่านตลอดกะ
แปลงทั้ง 39 จุดเป็นเฉด ink แล้ว ส่วนพื้น/จุด/ขอบยังใช้สีสดตามเดิมเพราะถูกต้องอยู่แล้ว

ผลพลอยได้: เฉด ink เป็น getter ที่เข้มขึ้นตามโหมดคอนทราสต์สูง ขณะที่สีสดเป็น `const`
จุดเหล่านี้จึงเพิ่งจะตอบสนองต่อโหมดคอนทราสต์สูงจริง ๆ เป็นครั้งแรก

**ทางเลือกสุดท้าย — พื้นสีสด + ป้ายสีเข้ม แทนพื้นเฉด ink + ป้ายสีขาว**

ตอนแรกแก้ปุ่ม/ชิปด้วยการเปลี่ยน "พื้น" เป็นเฉด ink แล้วคงป้ายสีขาวไว้ ซึ่งผ่านเกณฑ์จริง
แต่ทำให้จอครัวทึบลงจากเหลืองอำพันสดเป็นน้ำตาล ซึ่งเสียประโยชน์หลักของ KDS ไป —
ครัวอาศัย "ความสดของสี" ในการกวาดสายตาหาตั๋วที่ต้องทำจากระยะไกล ไม่ได้อ่านทีละใบ

จึงเปลี่ยนมาใช้คู่ที่ได้ทั้งสองอย่าง: **คงพื้นสีสดไว้ แล้วเลือกสีป้ายตามพื้น**

| พื้น | ป้ายขาว | ป้ายเข้ม | เลือก | ผล |
|---|---|---|---|---|
| เหลือง (รอทำ) | 2.13 | **7.93** | เข้ม | AAA |
| ส้ม (กำลังทำ) | 2.84 | **5.95** | เข้ม | AA |
| เขียว (พร้อมเสิร์ฟ) | 3.45 | **4.91** | เข้ม | AA |
| เขียวมิ้นต์ | 2.55 | **6.63** | เข้ม | AA |
| แดง | **4.51** | 3.75 | ขาว | AA |
| น้ำเงิน | **5.02** | 3.37 | ขาว | AA |
| ม่วง | **5.55** | 3.05 | ขาว | AA |

ทำเป็น helper สองตัวแทนการฮาร์ดโค้ดทีละจุด:

- `AppColors.fillOf(base)` — คืนสีสดในโหมดปกติ และเฉด ink ในโหมดคอนทราสต์สูง
  (โหมดคอนทราสต์สูงต้องการ AAA ซึ่งสีสดทำไม่ได้ทุกตัว — เขียวได้แค่ 4.91)
- `AppColors.onColor(background)` — เลือกป้าย "เข้ม" หรือ "ขาว" จากสีพื้นจริง
  โดยคำนวณคอนทราสต์ทั้งสองแบบแล้วเลือกตัวที่ดีกว่า ไม่ใช่จำว่าสีไหนใช้อะไร

ข้อดีของการคำนวณแทนการจำ: เพิ่มสีใหม่เข้าพาเลตต์แล้วป้ายถูกต้องเองทันที
และเทสต์บังคับได้ว่าทุกสีที่เอาไปเป็นพื้นต้องมีป้ายที่อ่านออก

**บั๊กที่เทสต์ชุดนี้จับได้ทันที** — `inkOf()` ไม่เคยแมป `info` ไว้เลย เพราะตอนเขียน
`infoInk` มีค่าเท่ากับ `info` เป๊ะ ๆ (เขียนไปก็ไม่มีผล) พอ `infoInk` แยกเป็นเฉดของตัวเอง
การลืมบรรทัดนั้นทำให้ `inkOf(info)` คืนสีเดิมกลับไปเงียบ ๆ ชิปและปุ่มสีน้ำเงินจึงไม่เข้มขึ้น
ตามโหมดคอนทราสต์สูงเลย — เป็นบั๊กที่มองด้วยตาไม่มีทางเห็น

**บังคับด้วย lint** — กฎ `use_ink_color_for_foreground` ดักการเอาสีสดไปใส่
`TextStyle(color:)` / `Icon(color:)` / `styleFrom(foregroundColor:)` บั๊กชุดนี้เกิดซ้ำ
สามรอบและทุกรอบหลุดสายตาไปได้ เพราะ "ดูแล้วก็อ่านออกอยู่" บนจอสะอาดในร่ม
รอบที่สามเจอเพราะถูกถามย้ำว่า "แก้หมดแล้วหรือยัง" ไม่ใช่เพราะมีอะไรฟ้อง

**ข้อเสียที่ยอมรับ** — โหมดคอนทราสต์สูงหน้าตาแข็งกว่าและ "สวย" น้อยกว่าโหมดปกติอย่างเห็นได้ชัด
เพราะขอบเข้มทำให้การ์ดดูเป็นกล่องมากกว่าลอย และปุ่ม/ชิปเปลี่ยนเป็นเฉด ink คู่กับป้ายสีขาว
(ต่างจากโหมดปกติที่คงสีสดไว้) ซึ่งเป็นการแลกที่ตั้งใจ — โหมดนี้เลือกอ่านออกกลางแดดก่อนความสด และยังไม่มีโหมดกลางคืนจริง ๆ
สำหรับร้านที่เปิดดึก ถ้าต้องการควรทำเป็น ticket แยกที่ตัดสินใจ palette ชุดที่สามโดยเฉพาะ

## 19. ใบกำกับภาษี — เลขที่รันรีเซ็ตทุกปี พ.ศ., ออกได้ 1 ใบต่อออเดอร์ที่จ่ายแล้ว, รองรับยกเลิก/ออกใหม่, snapshot ข้อมูลทั้งหมด

**ปัญหา** — ต้องออกใบกำกับภาษีตามข้อกำหนดกรมสรรพากร (มาตรา 86/4 เต็มรูป, มาตรา 86/6 อย่างย่อ)
โดยกฎหมายบังคับเรื่อง running number ต้องต่อเนื่องไม่ซ้ำ/ไม่ข้าม แต่ ticket ไม่ได้ระบุรายละเอียด
implementation ไว้ ต้องตัดสินใจเพิ่มหลายจุด (นโยบาย reset เลขที่, จุดที่ออกได้, การแก้ไข/ยกเลิกใบที่
ออกผิด, ความบังคับของเลขผู้เสียภาษีลูกค้า) — ตัดสินใจร่วมกับผู้ใช้ผ่านคำถามเลือกทางเลือกก่อนเริ่มเขียนโค้ด

**ที่เลือก**

- **รูปแบบเลขที่รัน `INV<ปี พ.ศ. 2 หลัก>-<เลขรัน 6 หลัก>` รีเซ็ตทุกปี พ.ศ.** (เช่น `INV69-000001`)
  คำนวณจาก `COUNT(*) WHERE running_number LIKE 'INV{yy}-%'` (นับรวมใบที่ถูกยกเลิกด้วย เพื่อไม่ให้เลข
  ถูกใช้ซ้ำ) — กฎหมายไทยอนุญาตให้แบ่งเลขที่รันเป็นหมวดตามช่วงเวลาได้ ตราบใดที่แต่ละหมวดยังต่อเนื่อง
  ไม่ซ้ำ/ไม่ข้าม จึงออกแบบให้ต่อเนื่องเฉพาะภายในปี พ.ศ. เดียวกัน (ไม่ต้องมีเลขยาวขึ้นเรื่อย ๆ ไม่มีที่สิ้นสุด)
- **ออกได้ 1 ใบต่อออเดอร์ เมื่อจ่ายครบแล้วเท่านั้น** (`order.status === 'paid'`) — บังคับด้วย partial
  unique index `CREATE UNIQUE INDEX ... ON tax_invoices(order_id) WHERE voided_at IS NULL` ทำให้มีใบ
  ที่ "ยังใช้งานอยู่" ได้สูงสุด 1 ใบต่อออเดอร์ในเวลาเดียวกัน โดยไม่ต้อง lock ระดับแอปพลิเคชันเพิ่ม เพราะ
  `better-sqlite3` เป็น synchronous และ Node.js เป็น single-threaded event loop จึงไม่มีการแทรกคิวขณะที่
  request handler เดียวกันยังทำงานไม่จบ
- **รองรับยกเลิก (void) ใบที่ออกผิดแล้วออกใหม่ได้** — เลือกทางนี้แทนทางที่แนะนำ (ออกครั้งเดียวแก้ไข/
  ยกเลิกไม่ได้เลย) เพราะร้านจริงพิมพ์ผิดประเภท/ข้อมูลลูกค้าผิดได้บ่อย การไม่มีทางแก้เลยจะสร้างภาระ
  บันทึกนอกระบบแทน — ยกเลิกเป็นการ "เติม" ไม่ใช่ "ลบ" (ตั้ง `voided_at`/`void_reason`/`voided_by` ไว้
  ถาวร ไม่ลบแถวทิ้งและไม่ใช้เลขที่เดิมซ้ำ) เก็บประวัติใบที่ถูกยกเลิกไว้ครบเพื่อการตรวจสอบ จำกัดสิทธิ์
  ยกเลิกไว้ที่ผู้จัดการขึ้นไปเท่านั้น (RBAC ระดับเดียวกับ refund)
- **เลขผู้เสียภาษีลูกค้า (`customerTaxId`) ไม่บังคับแม้ใบกำกับภาษีเต็มรูป** — บังคับแค่ชื่อและที่อยู่
  ลูกค้า สอดคล้องกับมาตรา 86/4 ที่ไม่ได้บังคับต้องมีเลขผู้เสียภาษีของผู้ซื้อ (ต่างจากอย่างย่อที่ไม่ต้อง
  มีข้อมูลลูกค้าเลย)
- **Snapshot ข้อมูลร้าน + ยอดเงินทั้งหมดไว้ที่ตัวเอกสารตอนออก** (`store_name`, `store_tax_id`,
  `store_address`, `store_branch`, `subtotal`, `vat`, `total`) แทนที่จะ join กับ `settings`/`orders`
  ตอนแสดงผล — ใช้แนวทางเดียวกับ snapshot โปรโมชันในข้อ 14 เพื่อให้เอกสารที่ออกไปแล้วไม่เปลี่ยนแปลง
  แม้ตั้งค่าร้านหรือ (ในทางทฤษฎี) ข้อมูลออเดอร์จะถูกแก้ภายหลัง
- **ฟิลด์ตั้งค่าร้าน (`storeTaxId`/`storeAddress`/`storeBranch`) ไม่บังคับกรอก** — ร้านที่ไม่ได้จด
  ทะเบียน VAT ไม่จำเป็นต้องมีเลขผู้เสียภาษี ระบบจะปฏิเสธการออกใบกำกับภาษี (HTTP 400) ก็ต่อเมื่อร้าน
  ยังไม่ได้ตั้งค่าเหล่านี้ไว้ แทนที่จะบังคับกรอกตั้งแต่ตอนติดตั้งระบบ

**ข้อเสียที่ยอมรับ** — เลขที่รันรีเซ็ตทุกปีทำให้เทียบเลขที่ข้ามปีไม่ได้โดยตรง (ต้องดูปี พ.ศ. ในเลขที่
ประกอบด้วย) และยังไม่รองรับ e-Tax invoice (ยื่นอิเล็กทรอนิกส์ต่อกรมสรรพากรโดยตรง) ตามที่ระบุไว้ใน
ticket ว่าจะเลื่อนไปเฟสถัดไป — เฟสนี้ออกได้แค่เอกสารที่ข้อมูลครบตามกฎหมาย ยังไม่เชื่อมต่อระบบยื่นจริง

## 20. Security hardening batch — fail-closed แทนการเตือนเฉยๆ ในทุกจุดที่เคยเจาะช่องโหว่

**ปัญหา** — ทำ security review เต็มรูปแบบ (OWASP Top 10) พบช่องโหว่ 7 จุด ตั้งแต่ High ถึง Low
ครอบคลุม broken access control, hardcoded secret, broken authentication และ security
misconfiguration — ต้องตัดสินใจว่าแต่ละจุดจะแก้แบบไหนโดยไม่กระทบ flow การใช้งานปกติของ
เดโม/ร้านที่ยังไม่ deploy จริง

**ที่เลือก** — ยึดหลักเดียวกันทุกจุด: **fail-closed แทนเตือนเฉยๆ**, ค่า default ที่ปลอดภัยสำหรับ
เดโม/dev ต้องไม่เปลี่ยนพฤติกรรม ส่วน production ต้องบังคับให้ตั้งค่าเองก่อนเสมอ

- **`JWT_SECRET` ไม่มี fallback ในโค้ดอีกต่อไป** (`config/env.js`) — เดิม fallback ไปใช้ค่า
  hardcode ที่เห็นได้จากซอร์สสาธารณะ ถ้าใครลืมตั้ง env ตัวนี้เท่ากับเปิดช่องให้ปลอม JWT สิทธิ์ admin
  ได้ทันที เปลี่ยนเป็น throw ตอน startup ถ้าไม่มีค่า
- **RBAC ของโมดูล users เพิ่มการเช็คลำดับสิทธิ์** (`user.service.js`) — เดิมมีแค่
  `authorize('admin','manager')` ระดับ route ทำให้ manager ตั้งรหัสผ่านใหม่ให้บัญชี admin หรือ
  เลื่อน role ตัวเองเป็น admin ได้ตรงๆ เพิ่ม `assertAdminBoundary()` บังคับว่าเฉพาะ admin เท่านั้น
  ที่แตะบัญชีระดับ admin ได้ (สร้าง/แก้ไข/รีเซ็ตรหัสผ่าน)
- **`authenticate()` เช็คสถานะจาก DB ทุก request แทนการเชื่อ JWT payload เก่า** (`middlewares/
  auth.js`) — เดิม role/is_active ที่ฝังใน token มีผลจนกว่า token จะหมดอายุเอง (สูงสุด 12 ชม.)
  แม้บัญชีจะถูกปิดใช้งาน/เปลี่ยน role ไปแล้ว เปลี่ยนเป็น query `userRepository.findById()` ทุก
  request แลกกับ DB read เพิ่ม 1 ครั้งต่อ request ซึ่งรับได้สำหรับสเกลร้านอาหารสาขาเดียว (ดูข้อ 6)
- **`DemoAccountPicker` (Flutter) gate ด้วย `AppConfig.demoMode`** (`login_page.dart`) — เดิม
  render ปุ่มกรอกบัญชีเดโมอัตโนมัติ (username/password ตรงกับ seed จริง) ในทุก build ไม่ใช่แค่
  demo build ย้ายเข้าไปอยู่ใน gate เดียวกับ banner
- **`CORS_ORIGIN` default เป็น string `'*'` ตรงๆ ไม่ผ่าน `.split(',')`** (`config/env.js`) — เดิม
  กลายเป็น array `['*']` ซึ่ง `cors` package เทียบแบบ exact-string จึงไม่ match origin จริงเลย
  (ปิดกั้น cross-origin ทั้งหมดโดยไม่ตั้งใจ) และปิด `credentials: true` เมื่อใช้ wildcard เพราะสอง
  อย่างนี้ใช้คู่กันไม่ได้ตามสเปก CORS/Fetch อยู่แล้ว
- **CSP เปิดไว้ทุกที่ยกเว้น `/docs`** (`app.js`) — เดิมปิด CSP ทั้งแอปเพราะ Swagger UI ต้องใช้
  inline script/style ทั้งที่ endpoint อื่นเป็น JSON ล้วน เปลี่ยนเป็นเช็ค path ต่อ request แทน
- **Seed บัญชีเดโมด้วยรหัสผ่านที่รู้อยู่แล้วไม่ได้อีกต่อไปถ้า `NODE_ENV=production`**
  (`db/seed.js`) — รหัสผ่านเดโม (`admin123` ฯลฯ) เผยแพร่อยู่ใน README/ซอร์สโค้ดสาธารณะ เดิม seed
  ทุกครั้งไม่ว่าโหมดไหน ทำให้ระบบที่ deploy จริงโดยไม่ได้อ่าน `SECURITY.md` ยังมีบัญชี admin ที่
  เดารหัสผ่านได้จากซอร์สโค้ดตรงๆ เปลี่ยนเป็นบังคับตั้งค่า `SEED_ADMIN_PASSWORD` (และอีก 5 ตัวต่อ
  บัญชี) ผ่าน env ก่อนเสมอเมื่อ production ไม่งั้น throw — ปิด `AUTO_SEED` แล้วสร้างบัญชีจริงเองก็
  ยังทำได้เหมือนเดิม (ตัวเลือกที่สองตามที่ `SECURITY.md` เคยแนะนำไว้)

**เหตุผลที่เลือก fail-closed แทนแค่ document/เตือน** — checklist ใน `SECURITY.md` เตือนเรื่องนี้
มาตั้งแต่แรกอยู่แล้ว แต่เป็นแค่คำแนะนำที่ต้องมีคนอ่านและทำตามเอง ไม่มีอะไรบังคับจริง — ถ้าจะให้
มั่นใจว่า deploy จริงจะไม่หลุดช่องโหว่ที่รู้อยู่แล้วว่าเป็นปัญหา ต้องทำให้ระบบปฏิเสธการรันแบบไม่
ปลอดภัยเอง ไม่ใช่หวังว่าจะมีคนอ่านเอกสารก่อน deploy ทุกครั้ง

**ข้อเสียที่ยอมรับ** — `authenticate()` มี DB read เพิ่มทุก request (ยอมรับได้ที่สเกลนี้ ดูข้อ 6)
และผู้ที่จะ deploy จริงต้องตั้งค่า env เพิ่มอีก 6 ตัวก่อน (หรือปิด `AUTO_SEED`) จะรันเปล่าๆ ด้วย
`NODE_ENV=production` โดยไม่ตั้งค่าอะไรเลยไม่ได้อีกต่อไป — เป็นการแลกที่ตั้งใจ เพราะ default เดิม
(รันได้เงียบๆ ด้วยรหัสผ่านที่รู้อยู่แล้ว) อันตรายกว่า

## 21. Audit log — snapshot ชื่อผู้ทำ, log อยู่ในทรานแซกชันเดียวกับการเปลี่ยนแปลงจริง, ขยาย scope เกินรายการขั้นต่ำในทิกเก็ต

**ปัญหา** — ไม่มี log ว่าใครยกเลิกออเดอร์/รายการ ให้ส่วนลดพิเศษ ปิดใช้งาน/ลบพนักงาน แก้ค่า VAT
หรือคืนเงินเมื่อไหร่และทำไม เปิดช่องให้พนักงานทุจริตหน้าร้าน (เช่น cashier ยกเลิกบิลหลังรับเงินสด
แล้วเก็บเงินเอง) โดยไม่มีทางตรวจสอบย้อนหลัง (ดู `docs/tickets/08-audit-log.md`)

**ที่เลือก**

- **ตาราง `audit_logs` แบบ append-only** — ไม่มี endpoint แก้ไข/ลบเปิดให้ใช้เลยทั้งระบบ (route
  เดียวคือ `GET /audit-logs` สำหรับ admin) `actor_user_id` เป็น `ON DELETE SET NULL` (ไม่ใช่
  `RESTRICT`) พร้อม snapshot `actor_name` ตรงๆ ในแถว — mirror ของรูปแบบเดียวกับ
  `promotion_name_snapshot`/`tax_invoices` (ดูข้อ 14/19) เพื่อให้ log ยังอ่านได้ครบแม้ผู้ใช้คนนั้น
  ถูกลบภายหลัง และลบ user ไม่ถูกบล็อกเพราะเคยมี log อ้างถึง
- **`auditLogService.log()` ถูกเรียกจากภายในทรานแซกชันเดียวกับการเขียนข้อมูลจริงเสมอ** (ไม่ใช่
  เรียกแยกหลัง commit) — ถ้าบันทึก log ไม่สำเร็จ การกระทำนั้นต้องล้มเหลวไปด้วยทั้งคู่ (rollback
  พร้อมกัน) แทนที่จะปล่อยให้การกระทำสำเร็จแต่ log หาย ใช้ `getDb().transaction()` แบบเดียวกับที่ใช้
  อยู่แล้วในทุก service (`order.service.js`, `user.service.js`, `settings.service.js`,
  `payment.service.js`, `tax-invoice.service.js`) จึงไม่ต้องเพิ่ม pattern ใหม่
- **log เฉพาะการกระทำที่ "เสี่ยงจริง" ไม่ log ทุกการแก้ไข** — ตัวอย่างที่ตั้งใจไม่ log: ยกเลิกรายการ
  อาหารตอนยัง `pending` (ยังไม่ส่งครัว ยกเลิกเองได้ปกติ ไม่ต้องขอสิทธิ์พิเศษ), แก้ชื่อพนักงานเฉยๆ,
  แก้ค่าตั้งค่าร้านที่ไม่ใช่ VAT/service charge (เช่น ชื่อร้าน/ที่อยู่) — ถ้า log ทุกอย่างจะกลืน
  สัญญาณของการกระทำที่เสี่ยงจริงจนหาไม่เจอ
- **ขยาย scope เกินรายการขั้นต่ำในทิกเก็ตอีก 3 action** เพราะเป็นการกระทำที่เสี่ยงต่อการทุจริต/
  privilege escalation แบบเดียวกัน และเพิ่งแก้ช่องโหว่ที่เกี่ยวข้องไปในข้อ 20:
  `user.role_change` (เปลี่ยนสิทธิ์พนักงาน), `user.password_reset` (ตั้งรหัสผ่านใหม่ให้พนักงาน),
  และ `tax_invoice.void` (ยกเลิกใบกำกับภาษี — เอกสารทางกฎหมายที่ยกเลิกแล้วกระทบยอดขาย)
- **Demo Mode mirror เต็มรูปแบบ** (`demo_store_audit_logs.dart` + `demo_store_settings.dart`
  ใหม่, wiring เข้า orders/auth/refunds/tax_invoices) — action/entityType/summary ตรงกับ backend
  ทุกจุด เพื่อให้หน้าจอ admin ในโหมดเดโมเห็นพฤติกรรมเดียวกับของจริง

**Frontend** — หน้า **ประวัติการทำรายการ** เห็นเฉพาะ `admin` เท่านั้น (ไม่รวม `manager` —
mirror ของ `authorize('admin')` ที่ route) filter ตาม action type ได้ด้วยชิปเลือก อ่านอย่างเดียว
ไม่มีปุ่มแก้ไข/ลบใดๆ ตาม acceptance criteria "append-only"

**ข้อเสียที่ยอมรับ** — `metadata_json`/`metadata` เป็น JSON แบบอิสระไม่มี schema บังคับต่อ action
(เทรดออฟความเร็วในการเพิ่ม action ใหม่ กับความปลอดภัยของ type) และหน้าจอ admin ยังไม่มี filter
ตามช่วงเวลาแบบ date picker (query parameter `dateFrom`/`dateTo` มีพร้อมใช้ที่ backend/repository
แล้ว แค่ยังไม่ต่อ UI) — เพิ่มทีหลังได้โดยไม่กระทบโครงสร้างเดิม

## 22. ลูกค้า/แต้มสะสม — แยก "ยอดที่นับเข้าออเดอร์" กับ "ยอดที่เก็บเงินจริง" เพื่อไม่ให้การใช้แต้มกระทบสถานะจ่ายครบ, ปฏิเสธแทนการปัดเศษ, reuse endpoint รายการออเดอร์เดิมสำหรับหน้าประวัติ

**ปัญหา** — ไม่มี table ลูกค้าในระบบ ผูกประวัติการซื้อกับลูกค้ารายบุคคลหรือทำระบบสมาชิก/แต้มสะสม
ไม่ได้ ซึ่งเป็นเครื่องมือการตลาดที่ช่วย retention (ดู `docs/tickets/09-customer-loyalty.md`)

**ที่เลือก**

- **`customers.phone` เป็น unique key หลักในการค้นหา/ผูกลูกค้า** — เบอร์โทรเป็นสิ่งที่ลูกค้าจำได้
  และพนักงานถามได้เร็วที่สุดตอนหน้าร้าน ไม่ใช้อีเมล (มักไม่มีตอนสั่งอาหาร) หรือเลขบัตรประชาชน
  (ละเอียดอ่อนเกินความจำเป็นของ POS ร้านอาหาร) `POST /customers` ปฏิเสธเบอร์ซ้ำด้วย 409
  ส่วน `orders.customer_id` เป็น nullable FK (`ON DELETE SET NULL`) — ลูกค้าทั่วไปไม่ต้องผูกก็สั่ง
  อาหารได้ปกติ ตรงตาม acceptance criteria "แบบ optional"
- **แยก `amount` (ยอดที่นับเข้าบัญชีจ่ายของออเดอร์) ออกจาก `chargedAmount` (ยอดที่ต้องเก็บเงินจริง
  ผ่านช่องทางที่เลือก) เวลาใช้แต้มแลกส่วนลด** — เก็บแค่ `pointsRedeemedValue` แล้วลบออกจาก
  `chargedAmount` เท่านั้น ส่วน `amount`/`alreadyPaid`/`isFullyPaid` ของออเดอร์ไม่ถูกแตะเลย
  เหตุผล: ถ้าลด `amount` ตรงๆ ตามมูลค่าแต้ม ออเดอร์ที่ลูกค้าใช้แต้มจนเกือบครอบคลุมทั้งบิลจะไม่มีวัน
  ขึ้นสถานะ "จ่ายครบ" เพราะยอดจ่ายสะสมนับได้น้อยกว่า `order.total` เสมอ ทั้งที่ร้านได้รับเงิน+แต้มที่
  หักไปครบตามมูลค่าจริงแล้ว การแยกสองยอดนี้ทำให้บัญชีของออเดอร์ถูกต้องเสมอไม่ว่าจะจ่ายด้วยเงินสด/
  QR ผสมแต้มกี่ครั้งก็ตาม (`payment.service.js#pay`, mirror ที่ `demo_store_payments.dart`)
- **แต้มที่ใช้แลกมีมูลค่าเกินยอดที่ต้องชำระรอบนี้ → ปฏิเสธ (400) ไม่ใช่ปัดลดให้อัตโนมัติ** — เลือก
  แบบเดียวกับแนวทาง error-first ที่ใช้ทั้งโปรเจกต์ (เช่นข้อ 20) เพราะการปัดลดเงียบๆ ทำให้แคชเชียร์
  ไม่รู้ตัวว่าจำนวนแต้มที่กดจริงกับที่ถูกหักไม่ตรงกัน ตรวจสอบและเขียนเทสต์ยากกว่าการปฏิเสธตรงๆ
- **สะสมแต้มคำนวณจาก `order.total` (ยอดเต็มของบิล) ไม่ใช่ยอดหลังหักแต้มที่แลกในรอบเดียวกัน** และ
  ให้ **ครั้งเดียวตอนออเดอร์เปลี่ยนเป็นจ่ายครบเท่านั้น** (ไม่ใช่ทุกครั้งที่มี payment record ใหม่) —
  กันแต้มพอกซ้ำตอนแยกจ่ายหลายรอบ (split payment) ต่อออเดอร์เดียว เก็บผลไว้ที่ `orders.points_earned`
  ครั้งเดียวเพื่อให้หน้าประวัติ/ใบเสร็จ query ย้อนกลับได้โดยไม่ต้องคำนวณซ้ำ
- **อัตราแลกแต้มตั้งค่าได้ที่ `settings`** (`pointsEarnRateBaht` จ่ายกี่บาทได้ 1 แต้ม,
  `pointsRedeemValueBaht` มูลค่า 1 แต้มตอนแลก) mirror รูปแบบเดียวกับ VAT/service charge ที่มีอยู่
  แล้ว — ไม่ log เข้า audit log ตอนเปลี่ยนอัตรา เพราะสอดคล้องกับขอบเขตเดิมในข้อ 21 ที่ log เฉพาะ
  VAT/service charge เท่านั้น ไม่ใช่ทุกฟิลด์ใน settings
- **หน้า "ประวัติการซื้อของลูกค้า" (admin/manager) reuse `GET /orders?customerId=` เดิม** แทนการทำ
  endpoint แยก (เช่น `/customers/:id/orders`) — ลดโค้ดซ้ำและได้ pagination/filter ที่ทดสอบแล้วมาฟรี
  โดยไม่ต้องเขียน endpoint ใหม่สำหรับ use case ที่เหมือนกันแค่กรองคนละมุม
- **ผูกลูกค้ากับออเดอร์ได้เฉพาะตอนเปิดออเดอร์ใหม่เท่านั้น** (ไม่รองรับตอนสั่งเพิ่ม/`POST
  /orders/:id/items`) — backend/ก็ไม่รับ `customerId` ในเส้นทางนั้นอยู่แล้ว เพราะการผูกลูกค้าย้อนหลัง
  หลังออเดอร์เปิดไปแล้วไม่ใช่ use case ที่ทิกเก็ตต้องการ (ค้นหา/ผูกตอนเปิดออเดอร์หรือตอนชำระเงิน)
  และเลี่ยงความกำกวมว่าแต้มสะสม/ประวัติของออเดอร์ที่เพิ่งผูกลูกค้าไปครึ่งทางควรนับยังไง

**Frontend** — `CustomerPickerDialog` (ค้นหา/สร้างลูกค้าใหม่) เรียก usecase ตรงผ่าน `Get.find`
แทนที่จะมี controller+binding แยก เพราะเป็นการดึงข้อมูลสนับสนุนแบบอ่านอย่างเดียว (mirror รูปแบบ
เดียวกับ `menu_form_page.dart`/`order_detail_page.dart`) เปิดจากแถบในตะกร้าตอนรับออเดอร์ ส่วน
หน้าชำระเงินโหลดข้อมูลลูกค้าเต็ม (รวมแต้มคงเหลือ) แยกจาก order object เพราะ `Order` เก็บแค่
`customerId`/`customerName`/`customerPhone` ไม่มี `pointsBalance` — ปุ่ม "ใช้สูงสุด" และตัวเลข
แต้มถูกจำกัดด้วย `maxRedeemablePoints` (min ของแต้มคงเหลือกับมูลค่าไม่เกินยอดจ่ายรอบนี้) ทุกครั้งที่
ยอดจ่ายเปลี่ยน กันผู้ใช้กดเกินโดยไม่ต้องรอ error จาก backend

**ข้อเสียที่ยอมรับ** — หน้าแยกบิลรายการอาหาร (split bill) ยังไม่มี UI ให้ใช้แต้มแลกส่วนลด (โครง
`pointsToRedeem` มีพร้อมที่ usecase/repository แล้ว แค่ยังไม่ต่อ UI) เพราะไม่ได้อยู่ใน acceptance
criteria ของทิกเก็ตนี้ — เพิ่มทีหลังได้โดยไม่กระทบโครงสร้างเดิม

## 23. Takeaway/Delivery — เลขคิวเฉพาะ takeaway ไม่รวม delivery, เพิ่มปุ่มเปิดออเดอร์ตรงแยกจากผังโต๊ะ, เชื่อม platform เดลิเวอรีตั้งใจไม่ทำ

**ปัญหา** — schema มี `orders.type: dine_in|takeaway|delivery` อยู่แล้ว แต่ UI/business logic
ทั้งหมดออกแบบมาสำหรับ dine-in เป็นหลัก (ผูกกับผังโต๊ะ) ไม่มีทางเปิดออเดอร์ takeaway/delivery ได้
เลยนอกจากยิง API ตรง ๆ และไม่มีเลขคิวรับอาหารให้เรียกลูกค้า (ดู
`docs/tickets/10-takeaway-delivery-flow.md`)

**ที่เลือก**

- **เลขคิวรับอาหาร (`orders.queue_number`) มีเฉพาะ `type = 'takeaway'` เท่านั้น ไม่รวม
  `delivery`** — คิวเลขเรียกมีไว้ให้ "ลูกค้ายืนรอหน้าร้าน" มารับอาหารเอง ส่วนออเดอร์เดลิเวอรีไม่มี
  ลูกค้ามายืนรอ ไรเดอร์จะอ้างอิงออเดอร์จาก `code` (เช่นที่ระบบขนส่งเดลิเวอรีจริงทำกัน) แยกแนวคิด
  ทั้งสองออกจากกันชัดเจนแทนที่จะให้เลขคิวความหมายกำกวมสำหรับทั้งสองประเภท
- **เลขคิวรันต่อวันแยกเป็นตัวนับของตัวเอง ไม่ใช้ตัวเดียวกับ `code`** — `code` เป็นเลขอ้างอิงของ
  ระบบ (ไม่มีใครอยากพูดว่า "ขอรับออเดอร์ ORD-20260915-0007") ส่วนเลขคิวต้องเป็นเลขสั้น ๆ ที่พนักงาน
  เรียกออกเสียงได้ง่าย (`nextQueueNumber()` นับเฉพาะออเดอร์ takeaway ของวันนั้น แยกจาก
  `nextCode()` โดยสิ้นเชิง — ดู `order.repository.js`)
- **เพิ่มปุ่ม "สั่งกลับบ้าน/เดลิเวอรี่" ที่หน้าผังโต๊ะ แยกจากการแตะโต๊ะ** — ก่อนหน้านี้ทาง UI ไม่มี
  ทางเปิดออเดอร์ที่ไม่ผูกโต๊ะได้เลย ทั้งที่ backend/`CartController` รองรับอยู่แล้วบางส่วน (ตอนแตะ
  โต๊ะไม่ได้ ระบบ default `orderType` เป็น takeaway ถ้าไม่มี tableId/existingOrderId — แต่บั๊กเดิม
  คือเช็คเงื่อนไขนี้อยู่ใน `if (args is Map)` เท่านั้น ถ้านำทางมาโดยไม่มี arguments เลยจะไม่ตกเป็น
  ค่าเริ่มต้นนี้ ยังคงเป็น `dine_in` แล้วโดน backend ปฏิเสธ 422 เพราะไม่มี tableId — แก้โดยย้าย
  เงื่อนไขออกมานอก `if` ให้เช็คเสมอไม่ว่าจะมี arguments หรือไม่)
- **ครัว (KDS) แยกป้าย/ไอคอนทั้ง 3 ประเภทชัดเจน** (โต๊ะ+ชื่อโต๊ะ / ถุงกลับบ้าน+"กลับบ้าน" /
  มอเตอร์ไซค์+"เดลิเวอรี") แทนที่ตรรกะเดิมที่เดาจาก `tableName != null` อย่างเดียว (ทำให้ delivery
  ถูกจัดเป็น takeaway ผิดๆ เพราะทั้งคู่ไม่มีโต๊ะเหมือนกัน) เปลี่ยนไปอ่านค่า `item.orderType` ตรง ๆ
  ซึ่ง backend ส่งมาให้อยู่แล้วในคิวครัว (`findItemsByStatuses` join `o.type` มาด้วยตั้งแต่ก่อน
  ทิกเก็ตนี้) — ไม่ได้แสดงเลขคิวบนตั๋วครัว เพราะพนักงานครัวไม่ต้องรู้เลขคิว (เอาไว้เรียกลูกค้าหน้าร้าน
  เป็นหน้าที่ของพนักงานเสิร์ฟ/แคชเชียร์)
- **ไม่เพิ่ม endpoint/logic ใหม่ให้ cashier เช็คบิล takeaway** — ตรวจสอบแล้วว่าหน้าเก็บเงิน/ใบเสร็จ
  ทั้งหมด (`checkout_page.dart`, `checkout_controller.dart`, `receipt_page.dart`) ไม่มีจุดใดอ้างอิง
  โต๊ะเลยตั้งแต่ก่อนทิกเก็ตนี้ (`order.displayTarget` แสดงชื่อประเภทออเดอร์แทนชื่อโต๊ะอยู่แล้วเมื่อไม่มี
  โต๊ะ) acceptance criteria ข้อนี้จึงผ่านอยู่แล้วโดยธรรมชาติของสถาปัตยกรรมเดิม แค่ต้องตรวจสอบซ้ำว่า
  ไม่มี regression ไม่ต้องเพิ่มโค้ดใหม่
- **ตั้งใจไม่เชื่อมต่อแพลตฟอร์มเดลิเวอรี (Grab/LINE MAN)** ตามที่ทิกเก็ตแนะนำเองว่าควรแยกเป็น
  ทิกเก็ตย่อยต่างหาก เพราะ scope ใหญ่และขึ้นกับ external API ของแต่ละเจ้าที่ยังไม่รู้ว่าจะเชื่อมกับ
  เจ้าไหนจริง (รูปแบบเดียวกับที่ตั้งใจ scope สาขาเดียวไว้ก่อนในข้อ 11) — ออเดอร์ที่รับจากแพลตฟอร์ม
  เดลิเวอรีตอนนี้ยังต้องคีย์เข้าระบบเองผ่าน type=delivery เหมือนเดิม

**พบระหว่างทำ (ไม่เกี่ยวกับทิกเก็ตนี้โดยตรง แต่แก้ไปด้วยเพราะแตะไฟล์เดียวกัน)** — `migrate.js`
ขาดรายการ `addColumnIfMissing` ของคอลัมน์ที่ทิกเก็ต 09 เพิ่มเข้า `orders`/`payments`
(`customer_id`, `points_earned`, `points_redeemed`, `points_redeemed_value`) ทำให้ฐานข้อมูลที่มี
อยู่แล้วตั้งแต่ก่อนทิกเก็ต 09 จะพังทันทีตอนอัปเกรด (query ที่อ้างถึงคอลัมน์เหล่านี้จะ error
"no such column") เพราะ `CREATE TABLE IF NOT EXISTS` ไม่แก้ตารางเดิมที่มีอยู่แล้วให้อัตโนมัติ —
เติมรายการที่ขาดให้ครบพร้อมกับเพิ่ม `queue_number` ของทิกเก็ตนี้เอง (ไม่ได้แก้ปัญหา CREATE INDEX
ที่อ้างถึงคอลัมน์ใหม่บนฐานข้อมูลเก่ามากไปกว่านี้ เพราะนอกขอบเขตทิกเก็ตนี้และไม่มีเทสต์คลุมสถานการณ์
อัปเกรดฐานข้อมูลเก่าอยู่แล้ว)

ด้วยซ้ำ — เท่ากับว่าทุกภาพที่ติดคำว่า "high-contrast" ในชื่อไฟล์ ถูกถ่ายด้วยโหมดปกติมาตลอด

**ทำไมไม่มีเทสต์ไหนจับได้มาก่อน** — `contrast_service_test.dart`/`app_colors_contrast_test.dart`
ทดสอบเส้นทางสลับโหมดจริง (ผ่านปุ่มในแอป) และค่าคอนทราสต์ที่คำนวณจาก token โดยตรง ซึ่งทั้งคู่ถูกต้อง
อยู่แล้ว — บั๊กอยู่เฉพาะในตัวเครื่องมือถ่ายภาพหน้าจอ (`tool/screenshots/`) ที่ไม่ได้อยู่ใน `test/`
และไม่มีอะไรเทียบภาพ 2 ไฟล์กันเองว่าต้องต่างกัน (golden test เทียบแค่ "ไฟล์นี้ตรงกับที่คอมมิตไว้
ไหม" ไม่เคยเทียบ "ไฟล์ A ต้องไม่เหมือนไฟล์ B")

**ที่แก้** — ย้ายการตั้งโหมดจาก `AppColors.contrast = ...` ตรง ๆ ไปเป็นการ seed
`StorageService` **ก่อน** สร้างแอป (`ScreenshotHarness.launchApp(..., highContrast: true)` เรียก
`storage.saveContrast('high')` ก่อน `Get.put<StorageService>(storage, ...)`) ให้เดินตามเส้นทางเดียว
กับตอนแอปเปิดจริง (`ContrastService.restore()` อ่านเจอค่าที่ seed ไว้แล้วตั้งถูกต้องตั้งแต่ build
แรก) ลบ `setUp`/`tearDown` เดิมที่ตั้ง static field ตรง ๆ ทิ้งเพราะไม่มีผลจริงอยู่แล้ว

**ผลหลังแก้** — regenerate ภาพทั้งชุดใหม่ มีแค่ 2 ไฟล์นี้เท่านั้นที่เปลี่ยน (ไฟล์อื่นอีก 27 ใบ
ไบต์เหมือนเดิมทุกอัน ยืนยันว่าไม่กระทบอะไรนอกเหนือจากนี้) เทียบแล้วเห็นความต่างจริงตามที่เอกสาร
ข้อ 18 อธิบายไว้ เช่นปุ่ม "เริ่มทำ" บนตั๋วครัวสลับจากพื้นส้มสด/ตัวหนังสือเข้ม เป็นพื้นน้ำตาลเข้ม/
ตัวหนังสือขาวเมื่อสลับโหมด (`AppColors.fillOf`/`onColor`) และหัวคอลัมน์ "รอทำ" เข้มขึ้นชัดเจน
(`AppColors.inkOf`) — นำภาพที่ถูกต้องไปใช้แทนในหน้า Landing Page ด้วย

**บทเรียน** — ชื่อไฟล์ที่บอกว่า "ภาพนี้คือโหมด X" ไม่ได้แปลว่าภาพนั้นถูกถ่ายในโหมด X จริง
ต้องตรวจสอบด้วยว่าค่า config ที่ตั้งไว้ก่อนถ่ายภาพ **อยู่รอด** จนถึงตอนที่ widget ถูกวาดจริงหรือเปล่า
โดยเฉพาะเมื่อโค้ดแอปเองมีจุด "restore ค่าจาก storage ทับทุกครั้งที่ build" อยู่แล้วเพื่อจุดประสงค์อื่น
(กันกระพริบตอนเปิดแอป) — จุดตรวจสอบที่ง่ายและตรงที่สุดคือเทียบ `md5sum`/ไบต์ของภาพคู่ที่ควรต่างกัน
ไม่ใช่แค่ดูว่าแต่ละภาพ "เปลี่ยนไปจากที่คอมมิตไว้" หรือเปล่า

## 25. Order audit trail — ขยาย audit log (ข้อ 21) ให้ครอบคลุม "ใครกดสั่ง/แก้ไขออเดอร์" ไม่ใช่แค่เหตุการณ์เสี่ยง

**ปัญหา** — ผู้ใช้ (เจ้าของโปรเจกต์) ขอฟีเจอร์ audit สำหรับทั้ง financial audit และผู้จัดการร้าน
ให้ตรวจสอบได้ว่า "ใครกดสั่งหรือแก้ไขออเดอร์" — audit log เดิม (ข้อ 21) บันทึกเฉพาะเหตุการณ์ที่
เสี่ยงต่อการทุจริตเท่านั้น (ยกเลิกออเดอร์, void รายการหลังครัวทำแล้ว, แก้ส่วนลด ฯลฯ) การเปิดออเดอร์
ใหม่และการแก้ไขรายการปกติระหว่างที่ยัง pending ไม่ถูกบันทึกเลย ไม่ใช่ gap ที่มาจาก PO gap analysis
เดิม (`docs/FEATURE-GAP-ANALYSIS.md`) แต่เป็นคำขอเพิ่มเติมภายหลัง (ดู
`docs/tickets/13-order-audit-trail.md`)

**ที่เลือก**

- **เพิ่ม action type ใหม่ 6 รายการเข้า infrastructure เดิมของข้อ 21** ไม่สร้างระบบ log แยก:
  `order.create`, `order.item.add`, `order.item.edit`, `order.item.remove`, `order.move_table`,
  `order.merge` — ใช้ตาราง `audit_logs` เดียวกัน, `auditLogService.log()` เดียวกัน, เรียกภายใน
  ทรานแซกชันเดียวกับการเขียนข้อมูลจริงเสมอเหมือนเดิม
- **`order.item.remove` ใช้ `entityType: 'order'` ไม่ใช่ `'order_item'`** — ต่างจาก
  `order_item.void` (ข้อ 21) ที่ item ยังอยู่ในตาราง (แค่เปลี่ยนสถานะ) รายการที่ถูก "ลบ" จริงจะหาย
  จากตาราง `order_items` ไปเลย ผูก log กับ `entityId` ของ item ที่ไม่มีอยู่แล้วจะลิงก์ไม่ได้ จึงผูก
  กับออเดอร์แทนและเก็บชื่อ/จำนวนรายการไว้ใน `metadata` แทน
- **`order.item.edit` log เฉพาะตอนแก้ "จำนวน" เปลี่ยนจริงเท่านั้น ไม่ log ตอนแก้แค่โน้ต** — โน้ต
  (เช่น "ไม่เผ็ด") ไม่กระทบยอดเงิน/บัญชี ไม่ใช่สิ่งที่ financial/manager audit ต้องการเห็น หลักการ
  เดียวกับที่ข้อ 21 ไม่ log การแก้ชื่อพนักงานเฉยๆ — log เฉพาะสิ่งที่กระทบตัวเลขจริง
- **`order.create` ผูก actor จาก `waiterId`/`currentUserId` ของออเดอร์นั้นโดยตรง** ไม่ต้องรับ
  `user` เพิ่มเป็นพารามิเตอร์ใหม่ เพราะ `create()` มี `user` (คนที่กดสั่ง) อยู่แล้วในทุก entry
  point (route ก็ auth ไว้แล้ว)
- **เจตนาไม่ log ทุก field แบบ diff ละเอียด** — เก็บแค่ summary (ข้อความอ่านง่าย) + metadata
  สำคัญ (ชื่อเมนู/จำนวนเก่า-ใหม่/โต๊ะต้นทาง-ปลายทาง) พอสำหรับตรวจสอบ ถ้า log ทุก field แบบละเอียด
  จะ noise สูงเกินไปสำหรับ POS ร้านอาหารที่มีรายการเปลี่ยนบ่อยมาก (เหตุผลเดียวกับข้อ 21 ที่ไม่ log
  ทุกการแก้ไข)
- **Demo Mode mirror เต็มรูปแบบ** (`demo_store_orders.dart` เพิ่ม `_logAudit` เข้าไปใน
  `createOrder`/`addItems`/`updateItem`/`removeItem`/`moveOrderTable`/`mergeOrders`,
  `demo_data_sources.dart` ส่ง `actorId: _auth.currentUserId` ให้ทุกเมธอดที่เพิ่มใหม่) —
  พฤติกรรมตรงกับ backend ทุกจุดเหมือนข้อ 21

**Frontend** — ไม่ต้องแก้ UI หน้า **ประวัติการทำรายการ** เลย เพราะ filter chip สร้างจาก
`AuditLogAction.all` อัตโนมัติอยู่แล้ว (ดู `audit_log_page.dart`) แค่เพิ่ม action constant +
translation key ใหม่ 6 คู่ (TH/EN) ใน `AuditLogAction`/`audit_log_translations.dart` ก็ขึ้น
filter chip และป้ายชื่อใหม่ให้อัตโนมัติ

**ข้อเสียที่ยอมรับ** — เพิ่ม log volume ขึ้นมากพอสมควร (ทุกออเดอร์/ทุกการเพิ่ม-แก้-ลบรายการ ไม่ใช่
แค่เหตุการณ์เสี่ยง) ต่างจากหลักการเดิมของข้อ 21 ที่ตั้งใจ log แค่ "เสี่ยงจริง" เพื่อไม่ให้สัญญาณ
จมหาย — ยอมรับเทรดออฟนี้เพราะผู้ใช้ระบุชัดว่าต้องการ accountability ระดับ "ใครกดสั่ง/แก้ไข" ทุกครั้ง
ไม่ใช่แค่กรณีน่าสงสัย ถ้า log volume เยอะเกินจนหน้าจอ admin ใช้งานยาก ควรพิจารณาเพิ่ม filter ตาม
ช่วงเวลา (date picker — ยังเป็นข้อเสียที่ยอมรับค้างจากข้อ 21 เช่นกัน) เป็นลำดับถัดไป

**ยังไม่ได้ทดสอบ** — เขียน/รัน backend test ครบ (`backend/tests/audit-logs.test.js`, 224 เคสผ่าน
ทั้งหมด) แต่ฝั่ง Flutter ไม่มี Flutter SDK ในสภาพแวดล้อมที่พัฒนา (sandbox ไม่มี `flutter`/`dart`
ติดตั้ง) จึงรีวิวโค้ด Demo Mode ด้วยมือแทนการรัน `flutter analyze`/`flutter test` จริง — ควรรัน
ยืนยันอีกครั้งในสภาพแวดล้อมที่มี Flutter ก่อน merge ถ้าเป็นไปได้

## 26. PromptPay QR — generate payload เองแทนพึ่ง payment gateway, mirror อัลกอริทึมเป็น Dart คู่กับ JS

**ปัญหา** — ระหว่างตรวจ `docs/FEATURE-GAP-ANALYSIS.md` ซ้ำ พบว่า `qr` ใน `PAYMENT_METHODS`
เป็นแค่ label ให้ cashier กดยืนยันเอง เหมือน `card`/`transfer` ทุกอย่าง ไม่มีการ generate QR
ตามมาตรฐาน PromptPay (EMV QR) เลย ทั้งที่เป็น gap เดียวที่เหลืออยู่ใน 🔴 Critical (ดู
`docs/tickets/16-promptpay-qr.md`)

**ที่เลือก**

- **Generate payload เองเป็น pure function ไม่พึ่ง payment gateway/npm package ภายนอก** —
  อัลกอริทึม EMV QRCPS Merchant Presented Mode (TLV + CRC-16/CCITT-FALSE) เป็นมาตรฐานสาธารณะที่
  เสถียร ไม่เปลี่ยนบ่อย เขียนเองสั้นกว่าและไม่ต้องเพิ่ม dependency ใหม่ฝั่ง backend — อ้างอิง
  โครงสร้างจาก `dtinth/promptpay-qr` (MIT, implementation อ้างอิงที่ใช้กันแพร่หลายที่สุดสำหรับ
  PromptPay ฝั่ง JS) และตรวจ CRC ด้วย test vector มาตรฐานของ CRC-16/CCITT-FALSE ("123456789" →
  `0x29B1`) ก่อนเอามาใช้จริง
- **Backend คำนวณ payload อย่างเดียว ไม่ generate ภาพ QR** — คืนเป็น string ให้ Flutter เรนเดอร์
  เป็นภาพเองด้วย `qr_flutter` (เพิ่ม dependency ใหม่ฝั่ง Flutter) หลีกเลี่ยงการส่งไฟล์รูปภาพผ่าน
  API และให้ Flutter ควบคุม UI/ขนาดภาพได้อิสระ
- **Mirror อัลกอริทึมเป็น Dart อีกชุดสำหรับ Demo Mode** (`app/lib/core/utils/promptpay.dart`)
  แทนที่จะบังคับให้ Demo Mode เรียก backend จริง (ซึ่งไม่มีให้เรียกตามนิยามของ Demo Mode) — เป็น
  โค้ดคำนวณที่ซ้ำ Dart/JS ตามหลักการเดียวกับที่ `docs/DECISIONS.md` #2 วางไว้ (bill calculation)
  จึงคุมด้วย **golden-value test**: คำนวณ payload ตัวอย่างเดียวกัน (เบอร์ `0812345678`, ยอด 100
  บาท) จากทั้งสองฝั่งแล้วยืนยันว่าได้สตริงตรงกันเป๊ะทุกตัวอักษร (`test/core/utils/promptpay_test.dart`)
  กันกรณี implement ผิดสเปกโดยไม่รู้ตัวข้างใดข้างหนึ่ง
- **เพิ่ม field `promptPayId` แยกจาก `storeTaxId` ที่มีอยู่แล้ว** — แม้ทั้งคู่เป็น "เลขประจำร้าน"
  เหมือนกัน แต่ร้านอาจอยากใช้เบอร์โทรเป็นเลขพร้อมเพย์ ต่างจากเลขผู้เสียภาษีที่ใช้ออกใบกำกับภาษี
  (คนละความหมาย คนละ validation length) — ใช้ตาราง `settings` key-value เดิม ไม่ต้อง migration
- **ไม่มี payment gateway/callback ตรวจสอบการจ่ายอัตโนมัติ** — ตามขอบเขตที่ gap analysis แนะนำไว้
  แคชเชียร์ยังต้องเช็คสลิป/แอปธนาคารเองก่อนกดยืนยันรับชำระ เหมือนช่องทางโอน/บัตรเดิมทุกประการ ไม่ใช่
  ฟีเจอร์ใหม่ที่ต้องเรียนรู้เพิ่ม
- **ยังไม่ได้ตั้งค่าเลขพร้อมเพย์ → 400 พร้อมข้อความแจ้งชัดเจน** ไม่ใช่พังเงียบๆ หรือคืน QR ที่ใช้
  งานจริงไม่ได้ (ทั้ง backend และ Demo Mode ใช้ข้อความเดียวกัน)

**ข้อเสียที่ยอมรับ** — โค้ดคำนวณ EMV QR ซ้ำกัน 2 ภาษา (JS ฝั่ง backend, Dart ฝั่ง Demo Mode) เพิ่ม
ภาระดูแลถ้าสเปกเปลี่ยน (ไม่น่าเกิดบ่อยเพราะเป็นมาตรฐานสาธารณะที่นิ่งแล้ว) แต่ golden-value test
ป้องกันไม่ให้สองฝั่งเพี้ยนออกจากกันโดยไม่รู้ตัว — ยึดหลักการเดียวกับ #2

## 27. Audit ระดับบัญชี/การเงิน — export CSV เป็น web-only ด้วย `package:web`, ไม่ใช้ `dart:html` ที่ deprecated แล้ว

**ปัญหา** — ticket 13 (ข้อ 25) ปิดฝั่งผู้จัดการร้าน ("ใครสั่ง/แก้ไขออเดอร์") แต่ตรวจโค้ดจริงพบว่า
ฝั่งบัญชียังไม่ครบ: `menu.service.js` (แก้ราคาเมนู), `promotion.service.js` (สร้าง/แก้/ลบโปรโมชัน),
`ingredient.service.js` (ปรับสต๊อกมือ) ไม่มีการเรียก `auditLogService.log()` เลย และหน้า "ประวัติการ
ทำรายการ" ไม่มีทาง export ให้ฝ่ายบัญชี ไม่มี date range picker (ของค้างจากข้อ 21) ดู
`docs/tickets/14-financial-audit-trail.md`

**ที่เลือก**

- **เพิ่ม action type ใหม่ 5 รายการเข้า infrastructure เดิมของข้อ 21/25** ไม่สร้างระบบ log แยก:
  `menu.price_change`, `promotion.create`, `promotion.update`, `promotion.delete`,
  `ingredient.stock_adjust` — `menu.price_change` log เฉพาะตอนราคาเปลี่ยนจริง (หลักการเดียวกับ
  `order.item.edit` ในข้อ 25 ที่ไม่ log ทุก field) ส่วนโปรโมชัน/สต๊อกกระทบยอดขาย/ต้นทุนโดยตรงทุก
  ครั้งจึง log ทุก action ไม่กรอง
- **Export CSV เป็น pure function แยกจากการ generate ที่ backend** (`backend/src/core/csv.js`,

  กัน Excel เปิดแล้วอักษรไทยเพี้ยน (Excel เดาเป็น ANSI ถ้าไม่มี BOM) — endpoint ใหม่
  `GET /audit-logs/export` reuse filter เดิมของ `GET /audit-logs` แต่ไม่มี pagination (ดึงทุกแถวที่
  ตรงเงื่อนไขครั้งเดียว เพราะ export ต้องได้ไฟล์ครบ ไม่ใช่แค่หน้าที่กำลังดูอยู่)
- **ดาวน์โหลดไฟล์ฝั่ง Flutter ใช้ `package:web` + `dart:js_interop` ไม่ใช้ `dart:html`** — `dart:html`
  ถูก mark `@Deprecated('Use package:web and dart:js_interop instead.')` ในเวอร์ชัน Dart SDK ที่
  Flutter 3.35.1 ล็อกไว้อยู่แล้ว การใช้จะทำให้ `flutter analyze` ไม่ผ่าน (ต้องได้ "No issues found!"
  เสมอ) จึงต้องใช้ทางที่ทีม Dart แนะนำแทนตั้งแต่แรก ไม่ใช่ hack ชั่วคราว
- **Conditional export/import แยก implementation ตาม platform ตอน compile** —

## 28. ปิดรู audit log ที่เหลือ — เปิด/ปิดกะ, รับชำระเงิน, กรอก/ถอดโค้ดส่วนลด

**ปัญหา** — self code-review รอบใหม่ (เช็ค clean code/tech debt/state management/architecture/
spaghetti risk ทั้ง backend และ Flutter) พบว่าแม้ข้อ 21/25/27 จะปิด gap ของ audit log ไปหลายชั้นแล้ว
ก็ยังมี 3 จุดที่กระทบเงิน/บัญชีโดยตรงแต่ไม่ log เลย:

1. `shift.service.js#open/close` — `close()` คำนวณส่วนต่างเงินสด (variance) ซึ่งเป็นเหตุการณ์เสี่ยง
   ทุจริตแบบเดียวกับที่ audit log ข้อ 21 ตั้งใจครอบคลุมไว้ตั้งแต่แรก แต่ไม่เคยเรียก
   `auditLogService.log()` เลยสักจุด
2. `payment.service.js#pay()` — รับชำระเงิน (รวมการใช้แต้มสะสมลดยอด) ไม่ log ทั้งที่ `refund()` ใน
   ไฟล์เดียวกัน log ทุกครั้ง — ทำให้ตรวจสอบย้อนหลังได้แค่ "เงินคืนเท่าไหร่" แต่ไม่มี "รับเข้าเท่าไหร่
   ใครรับ"
3. `order.service.js#redeemPromotionCode/removePromotion` — เขียน `updateTotals` ตรงๆ โดยไม่มีทั้ง
   `getDb().transaction()` ห่อและไม่มี audit log ทั้งที่ method พี่น้องในไฟล์เดียวกัน
   (`applyDiscount`) มีครบทั้งสองอย่าง — เสี่ยงทั้ง data integrity (เขียนไม่ atomic กับ log) และ
   ตรวจสอบย้อนหลังไม่ได้ว่าใครกรอก/ถอดโค้ดส่วนลดออกจากบิล

**ที่เลือก**

- **เพิ่ม action type ใหม่ 4 รายการเข้า infrastructure เดิมของข้อ 21/25/27** ไม่สร้างระบบแยก:
  `shift.open`, `shift.close`, `payment.pay`, `order.promotion_redeem`, `order.promotion_remove`
  (จริง ๆ คือ 5 action แต่ `shift.open`/`shift.close` นับเป็นคู่เดียวกัน) — ทุกจุด log ทุกครั้งไม่มี
  เงื่อนไขกรอง เพราะกระทบเงิน/ยอดขายโดยตรงทุกครั้งที่เกิด ต่างจาก `menu.price_change` (ข้อ 27) ที่
  กรองเฉพาะตอนราคาเปลี่ยนจริง
- **`shift.open/close` ห่อด้วย `getDb().transaction()` เพิ่มใหม่** (เดิมเป็นแค่ single UPDATE/INSERT
  statement ไม่มี transaction เลยเพราะไม่เคยต้องเขียนคู่กับอะไร) ให้ atomic กับ audit log write
  ตามหลักการเดียวกับทุก service อื่นที่มี audit log (ถ้า log ล้มเหลว การเปิด/ปิดกะต้องล้มเหลวด้วย)
- **`redeemPromotionCode`/`removePromotion` ห่อด้วย transaction ตามแบบ `applyDiscount`** ในไฟล์
  เดียวกันทุกประการ (ทั้งสองอยู่ใน `order.service.js`) แทนที่จะสร้าง pattern ใหม่ — ต้องแก้
  `order.controller.js` ให้ส่ง `req.user` ผ่านไปด้วย (เดิมไม่เคยส่งเพราะไม่เคยต้องใช้)
- **ไม่แตะ `customer.service.js`/`table.service.js`** แม้ตรวจพบว่าก็ไม่ log เหมือนกัน — พิจารณาแล้วว่า
  ความเสี่ยงต่ำกว่ามาก (สร้างลูกค้าใหม่/เปลี่ยนสถานะโต๊ะไม่กระทบตัวเลขทางบัญชีโดยตรงเหมือน 3 จุดข้าง
  ต้น) จึงไม่รวมในรอบนี้ ทิ้งไว้เป็นของที่พิจารณาเพิ่มได้ในอนาคตถ้าจำเป็น

**ข้อเสียที่ยอมรับ** — ไม่มี ทุกจุดที่แก้เป็นการเติมของที่ขาดตาม pattern เดิมที่มีอยู่แล้วในโปรเจกต์
ไม่ได้เปลี่ยน behavior หรือ trade-off ใหม่ใดๆ ที่ผู้ใช้จะสังเกตเห็น (audit log อ่านได้เฉพาะ admin
เหมือนเดิม)

## 31. บั๊ก `docs/video/build.sh` ตัดฉากปิดวิดีโอหายไปเงียบๆ — แก้ด้วย freezedetect แทนเลข hardcode

**ที่เลือก**

- **คำนวณความยาว timeline จาก `storyboard.py` โดยตรงในสคริปต์** (`sum(s['duration'] for s in
  scenes)`) แทน hardcode เลขไว้ในคอมเมนต์ — กัน bug ซ้ำเวลามีคนเพิ่ม/ลดฉากในอนาคตแล้วลืมแก้เลขนี้
- **อัดวิดีโอดิบยาวเผื่อไว้มาก** (`TOTAL + 60` วินาที) แทนที่จะคำนวณ multiplier ตายตัวจากอัตราส่วนที่
  วัดได้ในเครื่องนี้ครั้งเดียว — เพราะความช้าขึ้นอยู่กับสเปกเครื่องที่รัน ถ้า hardcode multiplier ตาม
  เครื่องนี้ (ช้า ~16-20%) เครื่องที่เร็วกว่าจะได้วิดีโอที่มีจอดำค้างท้ายยาวเกินไป เครื่องที่ช้ากว่าจะโดน
  ตัดฉากปิดหายอีกเหมือนเดิม
- **หาจุดจบจริงด้วย `ffmpeg -vf freezedetect`** — เลือก freezedetect เพราะฉากปิด/ฉากสถิติเล่นแอนิเมชัน
  reveal ครั้งเดียวจบแล้วค้างนิ่ง (ต่างจากฉาก "shot" ที่มี kenBurns ขยับต่อเนื่องทั้งฉาก จึงไม่ถูกจับเป็น
  freeze) หา `freeze_start` ตัวสุดท้ายที่ไม่มี `freeze_end` คู่กัน (แปลว่านิ่งไปจนจบไฟล์ที่อัดมา) นั่นคือ
  จุดที่ทุกแอนิเมชันในวิดีโอเล่นจบจริง เผื่อ pad ท้ายอีก 0.4s แล้วค่อยตัด — ได้ผลลัพธ์ที่ยาวพอดีอัตโนมัติ
  ไม่ว่าจะรันบนเครื่องเร็วหรือช้าแค่ไหน ไม่ว่า storyboard จะยาวขึ้นอีกแค่ไหนในอนาคต
- **fallback ถ้าไม่เจอ freeze ท้ายเลย** (เช่นเครื่องช้ากว่าที่เผื่อไว้มาก) ใช้ความยาวที่อัดมาทั้งหมดแทน
  พร้อม print warning — ยอมรับวิดีโอที่มีจอดำค้างท้ายเกินจำเป็น ดีกว่าตัดเนื้อหาจริงหายไปเงียบๆ แบบเดิม
- **เผยแพร่ไปพร้อมกัน**: แก้ bug แยกต่างหาก `${@:-th en}` ที่ quote ผิด (`"${@:-th en}"` ทำให้
  `th en` กลายเป็น argument เดียวแทนที่จะ split เป็นสองภาษา) เจอระหว่างทดสอบเรียก `./build.sh` แบบไม่ใส่
  argument (ค่า default ที่ตั้งใจให้ทำทั้งสองภาษา) — เคสนี้ไม่เคยมีใครทดสอบมาก่อนตั้งแต่เขียนสคริปต์นี้

**ข้อเสียที่ยอมรับ** — เวลารันสคริปต์นานขึ้นมาก (อัดดิบ ~170s/ภาษา แทน ~113s เดิม) เพราะต้องเผื่อ buffer

## 33. Ticket 15 — ผู้ช่วย AI ถามตอบข้อมูลร้าน (Ask-Your-Data) ผ่าน Claude API + tool-calling

**ปัญหา** — `docs/tickets/15-ai-ask-your-data.md` ตั้งใจให้เป็นจุดขายทางการตลาดว่า "เอา LLM มา
ประยุกต์ใช้จริง" ต่างจาก "chatbot ประดับ" ทั่วไปที่ตอบจากความรู้ทั่วไปของโมเดิลเฉยๆ ความเสี่ยงหลักคือ
LLM เดา/แต่งตัวเลขยอดขายเอง (hallucination) ซึ่งถ้าเกิดขึ้นกับข้อมูลร้านจริงจะทำลายความน่าเชื่อถือ
มากกว่าไม่มีฟีเจอร์นี้เลย

**ที่เลือก**

- **บังคับตอบผ่าน tool-calling เท่านั้น ห้ามมีทางตอบเป็นข้อความอิสระ** — เขียน manual tool loop เอง
  (ไม่ใช้ beta Tool Runner ของ SDK) เพราะ backend เป็น plain JS ไม่มี TypeScript loop เองทดสอบง่ายกว่า
  (inject fake client ได้ตรงๆ) และไม่ผูกกับ beta dependency — บังคับให้โมเดิลต้องเรียก tool
  `submit_answer` เสมอเป็นขั้นตอนสุดท้าย ผ่าน `tool_choice: {type:'tool', name:'submit_answer'}` ใน
  รอบสุดท้าย (`MAX_ROUNDS = 6`) ถ้าโมเดิลไม่ยอมเรียกเองก่อนหน้านั้น — กันทั้งการตอบมั่วแบบข้อความอิสระ
  และการวนเรียก tool ไม่จบ (ซึ่งเสียเงินจริงต่อ token)
- **แหล่งข้อมูลที่ผู้ใช้เห็น (`sources`) มาจากที่ระบบเป็นคนบันทึกเอง ไม่ใช่จากที่โมเดิลรายงานตัวเอง** —
  ทุกครั้งที่ tool ทำงานสำเร็จ ระบบ push `{tool, args}` เข้า `sourcesUsed` เอง โมเดิลไม่มีทางอ้างว่า
  ใช้ tool ที่ไม่ได้เรียกจริง เพราะ UI ไม่ได้เชื่อคำอธิบายของโมเดิล เชื่อแค่ log การเรียกจริงของระบบ
- **จำกัด tool ที่ยื่นให้โมเดิลเลือกตาม role ตั้งแต่ต้น ไม่ใช่กรองผลลัพธ์ทีหลัง** — `list_audit_log_entries`
  ยื่นให้เฉพาะ `admin` เท่านั้น (ตรงกับ `/audit-logs` เดิมที่สงวนไว้เฉพาะ admin) เพราะถ้าปล่อยให้
  manager เรียกได้ ผู้ช่วย AI จะกลายเป็นช่องทางเลี่ยงสิทธิ์ที่มีอยู่เดิมในระบบทันที
- **validate ซ้ำ input ของทุก tool ด้วย zod ก่อนเรียก handler จริงเสมอ** — SDK อาจ parse tool input ที่
  ถูกตัดตอนกลางแบบเงียบๆ ได้ ถ้าพารามิเตอร์ผิด schema (เช่น `limit` เกิน max) ส่ง tool_result แบบ
  `is_error` กลับไปให้โมเดิลแก้ไขเองแทนที่จะปล่อยให้ query พัง/คืนข้อมูลผิด

  ของจอเสมอสำหรับ `SnackPosition.TOP`) จึงแก้ที่ต้นตอจริง: ปิด `isDismissible: false` (ตัด
  `Dismissible`/gesture wrapper ออกไปเลย) เพราะ toast พวกนี้ auto-dismiss ตาม `duration` อยู่แล้ว
  ไม่มีเหตุผลต้องให้ปัดปิดเองด้วยซ้ำ — ยืนยันผลจริงด้วย Playwright: กดย้อนกลับได้ทันทีแม้ snackbar
  ยังค้างอยู่บนจอ คง `margin` ไว้ด้วยเหตุผลด้านสายตาอย่างเดียว (ไม่ให้ตัวการ์ดทับข้อความ AppBar)
